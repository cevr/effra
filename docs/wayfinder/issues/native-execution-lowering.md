# Direct native execution and matched build-cost receipts

Implement the [finite native lowering contract](../../specs/native-execution-lowering.md) using the canonical distinction between recipe construction and execution. Compare each candidate with an optimized idiomatic Go control and a TypeScript/Effect caller that preserve validation, rows, ownership, cancellation and cleanup; record erasure/direct lowering/retention plus residual allocation, dispatch, checks, executable bytes and retained modules. Native output must meet or exceed the optimized same-contract Go control before a performance claim. The retained long-body diagnostic and Go compiler profile identify a concrete factory/immediate-invocation cost; they are not performance superiority evidence.

Preserve lazy values, evaluation order, providers, cancellation, cleanup and all checked contracts. The existing emitter already provides comparison forms: the accepted multi-subject plan evaluates subjects once and emits ordered `if` branches with tag tests, while the current single-subject path emits a tag `switch`; effectful branches remain `yield* Effect.gen` and pure matches use an IIFE. These are output strategies, not performance results. For JS, pursue every material measurable improvement across those forms, direct dispatch and generated or specialized effect-runtime paths. Keep the pinned default Effect-compatible ABI and userland runtime contract, even when generated code is not human-style source. Retain cold/warm engine evidence, losing candidates and V8/runtime feedback limits; a many-times speedup is an ambition to test, not a promised multiplier. Compare general lowering strategies with identical runtime/dependency controls, stage-separated build receipts, exact generated artifacts and explicit cache/host conditions. Full conformance, gates, review and a repeatable matched improvement precede closure. Keep the historical package/cache HITL ticket separate.
