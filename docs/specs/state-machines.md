## Ordinary behavior, checked declaration

States and external events are nominal enums with payloads. Named functions perform step selection and completion handling using ordinary match and if expressions; they may be pure `fn` or `effect fn` with explicit failure and service rows (owner clarification, 2026-10-06). An entry function returns optional deferred work. One declaration binds these names and the initial state, giving the canonical plan a stable identity. One library runtime owns admission, entry, invocation and shutdown. No separate transition/guard/error-handling sub-language is needed.

General prerequisites are typed function/recipe values, finite rows, reusable generic enums and multi-subject/or-pattern matching. These serve other libraries too. The first profile permits one work recipe per entry and requires expected work failures to be explicitly recovered into a distinct outcome enum. Step and completion functions may declare expected failures directly or recover them into ordinary Step decisions. The union of step, completion and work service requirements is charged at spawn, with contribution paths retained; public spawning functions declare their own requirements. Step/completion failure rows remain part of the actor's terminal contract and the waiting call/observation contract. Immediate send reports admission only; it cannot pretend later execution has succeeded. Defects and interruption retain full Cause rather than becoming expected failures.

Illustrative, unimplemented syntax:

~~~rust
enum SessionState { Idle  Active { key: string } }
enum SessionEvent { Open { key: string } Close }

fn sessionStep(state: SessionState, event: SessionEvent) -> decision<SessionState, void> {
    match state, event {
        SessionState.Idle, SessionEvent.Open { key } => enter SessionState.Active { key }
        SessionState.Idle, SessionEvent.Close => ignore
        SessionState.Active { key: previous }, SessionEvent.Open { key } =>
            if key == previous { ignore } else { enter SessionState.Active { key } }
        SessionState.Active { key }, SessionEvent.Close => enter SessionState.Idle {}
    }
}

machine Session {
    initial SessionState.Idle
    step sessionStep
    enter sessionEnter
    complete sessionComplete
}
~~~

The other named functions have ordinary explicit signatures: enter is a pure fn taking State and returning an optional deferred Outcome recipe; complete takes State and Outcome and returns decision<State, Output>. All entry effects execute in that returned recipe under the entry scope. The declaration checks these against step and initial, and runs the static `stay` rule over step and complete. Definition constructs data; spawning starts managed work. Outcome and Event are different types, so public send cannot forge invocation completion. Constructing a recipe is distinct from executing it.

The same step interface admits effectful decisions without a second machine API. For example, an ordinary service call can validate an event before choosing the next state:

~~~rust
error AccessUnavailable

service Access {
    effect fn mayOpen(key: string) -> bool raises {AccessUnavailable}
}

effect fn sessionStep(state: SessionState, event: SessionEvent)
    -> decision<SessionState, void> raises {AccessUnavailable} uses {Access} {
    match state, event {
        SessionState.Idle, SessionEvent.Open { key } =>
            if run Access.mayOpen(key) {
                enter SessionState.Active { key }
            } else { reject }
        SessionState.Active { key: previous }, SessionEvent.Open { key } =>
            if run Access.mayOpen(key) {
                if key == previous { stay state }
                else { enter SessionState.Active { key } }
            } else { reject }
        SessionState.Idle, SessionEvent.Close => ignore
        SessionState.Active { key }, SessionEvent.Close => enter SessionState.Idle {}
    }
}
~~~

This alternative replaces the pure sessionStep above; it is not a duplicate declaration in one source file. A pure function retains the normal purity check. An effect function explicitly executes service work with run; the runtime executes that function's returned recipe once for the admitted event.

## Provider-independent plan

Checking produces one canonical plan from the declaration: nominal State/Event/Outcome/Output identities, the initial value, typed callable rows, possible transition outcomes, entry/work identity rules and bounded inspection facts. The plan is a provider-independent value; lowering may represent it for Go or JavaScript, while a provider supplies admission, evaluation, scopes, cleanup, scheduling and runtime snapshots. The compiler and parser do not select a builtin machine engine, and inspection never executes the plan.

Provider selection is an ordinary library/function/service operation with explicit requirements and failures. The planned first Effra provider will use the owned actor core, while ordinary actors remain usable without machine transitions. A provider must preserve the plan's nominal identities, rows and entry-epoch rules; incompatible providers and unsupported bindings diagnose through the normal contract checks. See the [provider contract](machine-provider-contract.md) for the separation and cross-provider acceptance.

## Explicit transition outcomes

Decision syntax makes lifecycle intent explicit. A step or complete function returns the predeclared `decision<State, Output>` and writes one of five forms (see [Decisions](#decisions)):

- `enter next` always closes the current entry and starts a new one, even for the same tag.
- `stay next` updates data while retaining the entry, timers and captured work input. Its tag must stay the same: reject visible violations statically and enforce dynamic values with a defined runtime defect and completed cleanup.
- `ignore` acknowledges without a state change. `reject` leaves state unchanged and reports a typed rejection to a waiting caller.
- `done output` publishes terminal output only after cleanup; bare `done` when `Output` is `void`.

Every state/event pair has a policy through ordinary exhaustive matching. Named variant or-patterns reduce repetition while preserving missing-pair diagnostics when either enum grows. Alternatives must bind the same names/types. Catch-all arms remain outside the initial closed-data policy. Ordinary unreachable-arm and type diagnostics handle duplicates and bad payloads. Bound product checking and plan construction rather than enumerating histories or exponentially expanding shared paths.

Conditions are ordinary total if/else expressions. A pure step/complete cannot execute effects; an effectful one may perform explicit run calls, including calls used to decide a transition. Requirements and failures survive helpers, aliases and provider capture through the common function/row representation. A capability query does not execute hidden work or rerun an effectful decision to discover whether an event is enabled.

Program-time delays are ordinary Clock/Scheduler work returning an outcome; no machine timer syntax is needed. The first profile is flat states and one work per entry. Hierarchy, parallel regions, history, eventless stabilization, supervision, postponement, multiple simultaneous invocations and durable replay remain unsupported. Unknown syntax diagnoses normally.

## Ownership and publication

One managed actor fiber owns its mailbox and state-entry scope. Each entry has a distinct epoch. Invocation outcomes carry actor generation, entry epoch and work identity; validate them at dequeue, including exit then re-entry into the same tag. Discard stale outcomes and count them in bounded inspection. Cancellation does not replace this check: a result may already be queued. A foreign completion adapter also carries the epoch; fencing cannot undo an external side effect.

Step and completion evaluations are serialized, including their effects, in a temporary scope directly owned by the actor, never by the current entry. At most one evaluation is in flight. The current entry stays owned while a decision is evaluated; external events and work completions remain queued under the spawn budgets. A successful evaluation first closes its own scope, interrupting unjoined children and awaiting finalizers. `enter` and `done` then close the old entry. Only successful completed cleanup permits commit and publication, followed by new entry work when applicable. Expected child interruption at scope close is not a fabricated failure. Work that must outlive the decision belongs in enter's recipe. Failure leaves the last stable state uncommitted, stops the actor after cleanup, and preserves the declared failure plus any cleanup cause. An application that wants to continue after a business failure explicitly recovers to `reject`, `stay` or another decision. No hidden retries or evaluation for inspection are allowed.

Stop cancels an in-flight evaluation and waits for its children/finalizers and the entry's cleanup; it prevents a subsequent commit. Stop does not drain: discard and count queued events/completions and complete their pending calls with Stopped. Drain is unsupported in the first profile. Commit and stop admission are serialized: Done committed first remains the single output observed by all waiters; stop admitted first prevents that commit. Stop during protected cleanup waits for cleanup and prevents new entry work. Cancelling a call waiter does not retract an already admitted event or abandon actor-owned work. State/output values cannot carry resources owned by the completed evaluation or a closing entry; Outcome values cannot carry entry-owned resources beyond that entry. Use the common ownership checker. State commit ordering does not roll back external writes performed by an effectful step. Transactions, idempotency and compensation remain explicit application/service contracts.

`enter` invalidates the old entry, requests cancellation and awaits its children/finalizers before publishing the next stable state and starting its work. `stay` preserves entry identity. Completion of an invocation does not by itself release resources owned for the whole entry. Cleanup defects fail the pending acknowledgement and stop the actor after cleanup, preserving composite causes. Expected cancellation of replaced work is not a newly fabricated domain failure. Final output and stop completion follow actor cleanup; concurrent stop callers observe one completed exit, and interrupting a waiter does not abandon cleanup.

Spawn requires explicit mailbox item/byte budgets, chosen as for [any actor](actors.md#proposed-library-surface): finite, or an explicit `unbounded` that the `no-unbounded-mailbox` lint asks the owner to justify. First-profile send admits immediately or fails with MailboxFull/Stopped; it never waits for queue capacity. Call uses that admission policy, then interruptibly awaits the committed transition, including completed old-entry cleanup and admission of new work; acknowledgement does not wait for the work's eventual outcome. Reject reports a typed Rejected failure.

The shared actor adapter also requires explicit payload/result snapshot limits, chosen as for [any actor](actors.md#proposed-library-surface): finite, or an explicit `unbounded` that the `no-unbounded-mailbox` lint asks the owner to justify. MessageTooLarge is an explicit admission failure for send/call; an oversized final Output stops with terminal MessageTooLarge rather than publishing success. That fixed terminal failure is charged at spawn and included in result observation, alongside the declared step/completion row. Payload/Output admission follows the shared portable-data and closed-owner checks, not host shallow copying.

The machine adapter produces `Actor<Session>` for a named Session machine: the machine declaration contributes its canonical event/request protocol, rather than treating Event as a service. Public send/call/result types and rows follow from that declaration, including through an annotated handle parameter. Event/Outcome/Output identities remain canonical; entry/transition policy and lifetime provenance are additional checked evidence, not requirements on ordinary service actors. Common awaitExit returns a P-independent bounded portable exit snapshot, preserving cause structure with safe snapshots/redacted tags and explicit truncation, never raw factory-typed or closed-owner payloads. Internal Cause remains complete. Separate machine result observation returns Output or raises the declaration's terminal row/Stopped; other terminal causes become Stopped with bounded portable cause data. Inspectable contracts are derived from the named declaration rather than caller-written bookkeeping parameters:

| Operation | Expected failures and requirements |
| --- | --- |
| Send | MailboxFull, MessageTooLarge or Stopped; admission carries no later step failures. |
| Call | MailboxFull, MessageTooLarge, Stopped, Rejected and the step's declared failures. Only the originating event's call receives its step failure; other queued calls receive Stopped with inspectable terminal cause data. |
| Result observation | The union of step/completion failures, fixed terminal MessageTooLarge and Stopped; successful completion returns Output. Completion failures have no originating event call. Other terminal causes become Stopped with portable cause data. Common awaitExit instead returns the P-independent completed exit snapshot. Factory-specific typed recovery stays at the spawn-site row. |
| Spawn | Constructor and step/completion/work service requirements; constructor/constructor-child failures and step/completion/fixed MessageTooLarge terminal failures are conservatively charged, following the fork rule. Unobserved terminal Cause propagates at owner closure; observing it does not erase the charged row. |

Defects, interruption and composite causes retain the runtime cause structure through every operation. A channel's expected-failure row must not flatten a cleanup defect or reattribute another event's domain failure.

One work per entry reserves one bounded completion slot at entry start; it and external events use a common arrival sequence. A completion arriving during evaluation waits in the slot: `enter` and `done` invalidate its epoch, while `stay` preserves it and arrival order. Stop has a separate control signal. Saturation cannot prevent completion or shutdown. No actor handle is automatically supplied to work, but aliases may still reach it. SelfCall uses the shared blocking-dependency rule: reject a self-call from an in-flight step/completion evaluation, its descendants or cleanup, not actor identity alone. Independent entry work may call its own actor; an `enter` or `done` decision closes the old entry and interrupts its waiter, which detaches without retracting the admitted event. Self-send through aliases remains nonblocking and never recursively processes a transition. A nonblocking stop request is allowed; any actor-owned execution, including entry work, awaiting its own actor exit produces the defined self-wait defect. Cross-actor waits may form cycles and remain outside the first profile's deadlock guarantee. Propagating a call chain alone cannot detect independently initiated mutual waits; do not advertise it as general cycle prevention. Ordinary explicit timeouts and cancellation remain available, with their normal rows and cleanup contract.

Tests use causal signals and repaired program-time scheduling; the independent watchdog remains wall clock. Unobservable foreign blocking remains an explicit deterministic-testing limitation.

## Inspection and boundaries

CLI/MCP project one canonical plan: source revision; State/Event/Outcome identity; initial state; function contracts and owners; possible enter/stay/ignore/reject/done edges; and terminal output. A bounded local walk identifies literal constructor targets; helper/dynamic results produce a conservative target set labeled as such. Never pretend this graph proves reachability, liveness or current enabledness. General product-match checking must be bounded without expanding all histories or shared type paths.

Runtime snapshots expose actor/entry identity, state tag, queue usage, lifecycle status (including an in-flight step/completion) and bounded causes/counters. They return the last committed state without waiting for application evaluation. The plan labels pure versus effectful functions, terminal-on-failure rows and directional contribution paths. Locally identified edges beneath an effectful condition carry that condition's contribution path; dynamic helper destinations remain conservative. Inspection never executes behavior, including pure steps; there is no enabledness query in the first profile. Payload exposure requires an explicit codec. Static possible edges, active runtime state and observed completed transitions are distinct.

Optional state snapshots use a named versioned codec and explicit restart/recovery policy. Scopes, fibers, service instances and in-flight host work are not serialized domain state. Starting from stored state invokes entry work again; idempotency, transactional admission, outbox and crash recovery remain separate obligations. No durable or exactly-once guarantee is implied.

## Construct admission gate

Status: DECIDED, 2026-10-07. `machine` is an admitted declaration with a narrow scope: KEEP under [construct admission](../design.md#language-design-principles) and its refinement that compiler-special behavior is spelled as a visible construct, never hidden in a library API.

**Evidence.** The machine admission probe spike (34 probe programs) showed that the same-tag `stay` guarantee needs compiler knowledge. Both tags inhabit the state type, so generics cannot reject `Idle` returning `stay Active { … }`; a checker rule keyed on decision syntax, binding records and match narrowing can. (The probes used the bundled `Step` enum, recognised by template identity; decision syntax replaced it, see [Decisions](#decisions).) The spike also built the library alternative, a `Machines.Plan` whose rows travel in callable-kind parameters with a structural six-argument `MachineActor<…>` handle. It typed handles soundly, but it carried a machine-specific compiler check behind an API, and its "only S-typed parameter" heuristic wrongly rejects a helper whose S parameter is not the current state: a step that names no current-state parameter cannot be checked for `stay`. The owner rejected that alternative: a special compile check for machines is a language construct.

**Scope.** The declaration binds `initial`, `step` and optional `enter` and `complete` to ordinary named functions. Behavior stays in those functions; there is no transition, guard or error-handling sub-language.

**What the declaration owns.**
- *The static `stay` rule*, as part of declaration checking. The declaration names the current state: the first parameter of `step` and of `complete`. Inside a match arm that narrows the current state, a constructed `stay` operand must be the single variant the arm narrows to. An or-pattern cell that narrows to several variants, such as `SessionState.Idle | SessionState.Active { key: _ }`, accepts only `stay state`, the unchanged subject. Without narrowing the value is dynamic, and the runtime defect applies. The rule follows the current state into helpers through the argument that carries it, so a helper whose S parameter is something else is not misjudged. It keys on decision syntax (the `stay` form) and binding records, never on a library declaration, and applies to pure and effectful functions alike. It is mandatory, never a lint. Its diagnostic code is EF139; it is not EF138, which codecs use.
- *The rows.* The declaration is the nominal home of the step and completion failure rows and of the step, completion and work service rows. Spawn charges them, and `Actor<Session>` names the declaration, so public operations and rows follow from it without a caller-written tuple or row parameters on data types.
- *Plan identity.* The declaration is the stable identity that graph tooling projects, with the bounded, non-executing walk that [inspection](#inspection-and-boundaries) specifies.

**Prior art.** No compared system checks same-state statically: XState v6 avoids it with a targetless keep transition; effect-machine and gen_statem compare tags or terms at runtime; gleam_otp and Akka have no such check. All of them type handles structurally or by message type. Effra's compile-time `stay` rule is new, and it is the reason the declaration exists.

**Remaining prerequisites, all general.** Errors declared by distributed modules, and distributed spawn with the actor runtime. Constructor-argument inference from the expected type is ergonomics only.

## Implementation status (2026-10-09)

The declaration, its checks and its inspectable plan have landed; the runtime has not. What exists:

- **Syntax.** `machine Name { initial <expr>; step f; enter g; complete h }` at top level, one binding per line in source order, formatted canonically. Type parameters, unknown or duplicate bindings, a bound name followed by `.`, `(` or `<`, and statechart words (`states`, `on`, `after`, `always`, `invoke`, `entry`, `exit`, `parallel`, `history`, `guard`, `context`, `actions`, `final` and similar) are EF002 parse diagnostics that say where that behavior belongs.
- **Decisions.** The predeclared `decision<S, O>` and the forms `enter e`, `stay e`, `ignore`, `reject` and `done e` (bare `done` for a void output), written the same way as patterns; see [Decisions](#decisions). They replaced the bundled `Step` enum of `ergo/machines`, which the checker recognised by template identity; that module is removed.
- **Declaration contract (EF140).** `step` is a pure or effect function `(S, E) -> decision<S, O>` whose first parameter is the current state. `S` is a closed, non-generic user enum, and `E` is a distinct closed user enum. `complete` takes the same `S` and `O` and an outcome type distinct from `E`, so an event cannot forge a work completion. `initial` is a literal constructor of `S` with a static payload. Ordinary match diagnostics (EF117 missing or unreachable pairs, EF121 binder consistency, EF137 coverage budget) apply unchanged because step functions are ordinary code, and so do undeclared failures and missing services (EF108).
- **Static `stay` rule (EF139).** As specified in the [admission gate](#construct-admission-gate). It is keyed on binder identity, so shadowing is exact and `let` alias chains of any length resolve to the binder they name. Or-pattern arms that admit several variants accept only `stay state`. The rule follows helpers to depth 4 through the argument that carries the state, and anchors the diagnostic at the caller's call site, naming the helper chain. A deeper chain is refused with EF142 when the state is narrowed at the call or the call passes the current state, because the rule could not judge a `stay` inside it. Otherwise every `stay` in the chain is unnarrowed and dynamic, and the conservative decision recorded for it is exact. Recursion is analysed per context. A context is the function, the state and trigger narrowing, and which parameters receive the current state and trigger. A recursive call is reused only when a visit already in progress covers its context: same function and bindings, a non-nil state narrowing that is a superset, or the unnarrowed state for an unnarrowed call. Otherwise the body is walked again under the new context, so a `stay` admitted on an unnarrowed first visit is judged again when recursion reaches it narrowed. Contexts are finite and a covered one is never re-walked, so the analysis terminates. Each walk is charged, and the helper depth bounds the chain. An unnarrowed literal `stay` is dynamic and left to the runtime defect. The stricter reading, which rejects every literal `stay` outside narrowing, was considered and rejected because the gate's text makes that case dynamic. The spike's 18 probes are ported in `internal/compiler/testdata/machines/`, with two corrections. A helper whose state parameter comes second is now checked through that parameter. A helper whose S parameter is not the current state is accepted, which fixes the spike's false positive.
- **Not yet admitted (EF141), never passed through.** The checker refuses three things:
  - *`enter`.* Its deferred `Outcome` recipe needs typed recipe values (#52), payload-aware recovery of work failures (#19) and checked entry ownership (#11, #47). Because `enter` is refused, `complete` without `enter` is an EF140 contract error.
  - *Using a machine name as a value.* That would be spawn or `Actor<M>`, which needs #11 and #47.
  - *Non-portable payloads.* A conservative data-only check refuses callables, recipes, provider recipes and host, provider or runtime handles in `S`, `E` and `O` payloads until portable ownership (#11) owns this rule. It is a reachability search that inspects each type once, so nesting depth and shared types cannot hide a callable.
- **Budgets (EF142).** 256 declarations per module, and 4,096 transitions and a 65,536-unit analysis budget per declaration. All declarations of a module also share a 1,048,576-unit budget. Resource closure is structural: analysis runs in its own package (`internal/compiler/machineplan`, see *Three phases* below), and every value whose size the program controls is built there by one charged builder, which charges the value's width before allocating it. That covers narrowings, lists and text:
  - *Narrowings* are canonical sorted variant positions, interned per enum, so equal narrowings share storage. Refining one by a match cell is charged by the cell's width and memoized by narrowing and cell.
  - *Lists* include walked expressions and block statements, collected state paths, helper scopes and visit contexts, alias steps, inspected payload types and fields, and each published transition's From, On, Targets and Via lists. They also include the plan's per-state facts, and the bound functions' failure and service rows charged by width. A block statement pays for its scope entry before it is inserted, and a refusal ends the block.
  - *Text* (plan IDs, diagnostic messages, type displays, payload paths and the declaration qualifiers the checker rebuilds) is charged by bytes, one unit per 64 bytes. Copying one long identifier into many strings therefore costs in proportion to the bytes copied. Key text the checker builds from a type (its public-ID key and the interning keys a template substitution rebuilds) is charged by a bound computed from the type's nodes: names, declarations, argument counts and row labels, summed over the tree the type unfolds to. A type display is charged by what building it allocates: wrapper types (`Effect<…>`, fibers, Go results and tuples) copy the display below them at every layer, so the charge grows with nesting depth times the text below. Each distinct node is walked once per module and charged, so a type whose unfolding is exponential is refused by its charge.
  - *Template-argument walks.* Substituting an application's arguments into its template's fields validates each argument again for every field. The layout charges, per field, the declared field type's nodes plus, for each application in it, the nodes of the substituted argument (one unit per 8 nodes). The checker instantiates the fields while preparing only when that cost fits the analysis budget, so an exponential instantiation is refused before it is built. Node counts come from the same memoized walk as the key-text bound: tree sums, capped where the checker's own walks stop, so shared nodes are over-counted rather than missed.
  - *Projected values* build no program-sized text: their contract and result already have public IDs (declaration publication interns every signature type before machines are checked), and their success display is a retained name. Projection checks both and refuses the declaration (EF142) if either fails, rather than projecting unbounded.
  - *Fixed per-declaration state* (the plan, its copy into the module's result, the declaration's analysis record, scopes and payload walks, and the first group of each map it creates) is charged by bytes before the plan is allocated. The map bytes are an estimate derived from the Go swiss-map layout (a 48-byte header, then a group of 8 slots behind an 8-byte control word, rounded up to a size class), and a test measures each listed map against it. For the checker's value type the fixed charge is 171 units (`machineplan.DeclarationUnits`). It was an estimated 114 units before it was derived, so modules now admit fewer large declarations. With at most 256 declarations, the 57 units more per declaration take at most 14,592 units, 1.39% of the module budget. A test pins that limit: of 256 declarations with 800 states each, exactly 209 are admitted before the shared budget refuses the rest, against 211 at the earlier estimate. A recorded diagnostic is counted as its buffer slot and deduplication entry. The EF142 that exhausts a budget is recorded after the budget is gone, so it is built uncharged, and it quotes at most 64 bytes of the machine name, followed by an ellipsis and the name's length. The result holds exactly the published plans, so it never grows by doubling.
  - *Three phases.* The checker runs machine analysis as prepare, analyse and commit:
    - *Prepare* is checker work. It checks each `initial` value as an ordinary expression in the checking pass, lowers the declarations and the function bodies the walk can read, and resolves the types, layouts (instantiating templates), displays and projections analysis reads into an immutable input. It follows the analysis order and charges the layouts and displays it builds, the payload walks it follows and the rows an effectful initial shows, with the same cost model against the same per-declaration and module limits. Those charges are, at every point, a subset of what analysis charges, so analysis finds prepared everything it can afford. A test pins the cost model's value term by term, and another pins the walk's and the rows' charges by the units each adds. Work over data the module shares is done once per module: a type whose whole reachable payload a walk has finished and found admissible is clean for the module, so a later walk from any root of any declaration stops there for one unit, and a row's display is paid by the first initial that shows it. Cleanliness is decided per strongly connected component (Tarjan's algorithm), since a type on a cycle is admissible only once its whole cycle is; a walk that ends at a refusal or at the budget marks nothing it has not finished. A test witnesses each of those two guards with the plan or refusal it protects. A declaration's preparation work therefore does not grow with the shared data: a test checks that 255 more declarations add the same units over 2,000 shared records, or 5,000 and 20,000 labels, as over 10, and the seed sweep holds what its shared-data axes add to the preparation bound of what they add. A fact it did not prepare is refused with EF142 when analysis reaches it, never guessed. The checker has no allocation budget of its own, so the mirror is what bounds preparation. A layout or display that analysis could never afford is not built, and every measured compile checks that no prepared one costs more than a declaration's budget, and that all of them together cost no more than the module's. Every measured compile also holds preparation's allocation to 512 bytes per unit its mirrored charges accepted, plus 64 bytes per source byte for what it builds without charging (lowered declarations and bodies, the type table, projections of published values), plus a 64 KiB allowance. The type table shares the checker's interned rows rather than copying them: rows are not linear in the source, since a chain of n `.catch` calls interns n rows of up to n labels from O(n) bytes, and a test holds that chain to the bound (a copy per row took 2.4 times it at 500 errors and 16 times at 4,000). The accepted units never exceed the module budget, so preparation is linear in the source. Every measured compile means the test compiles: the probe that checks the bound is unset in production. The layout's key-text charge is what holds back the dominant growth: k instantiations of a template whose F fields name an N-byte type rebuild k·F·N bytes of interning keys from a source of about F·N bytes, and `TestMachinePreparationAllocationIsCharged` fails without that charge. What preparing allocates (arena nodes, interned keys, checked values) is checker growth, counted against preparation's own bound rather than the analysis window.
    - *Analyse* is a function of that input alone. The package cannot import the checker, so it cannot reach the checker's arenas, intern maps or diagnostics; a test pins its imports and keeps its input and result plain data. Neither the package nor `machineplan/shared` imports `reflect` or `unsafe`, or holds a non-Go source file, and the test refuses all of them: those are the routes past Go's export rule. The fixed sizes analysis charges are counted in machine words, and a test checks each against `reflect`; a plan holds the checker's value type by value, so the checker passes its size in the input (`PlanBytes`). The input copies every slice it would otherwise share with the checker, except row labels: the checker writes those once, when it interns the row, and its own projections already share them. Analysis sees each shared row as a `shared.Row`: its labels are an unexported field of the package `machineplan/shared`, which exposes only reads and copies (`Len`, `At`, `All`, `Bytes`, `Join`, `AppendTo`). Code in the analysis package therefore has no way to write a label or append into a row's backing array, through any alias, conversion or container: a direct write does not compile, and the one route around the export rule, `reflect` or `unsafe`, fails the import test. A test pins the view's shape (one unexported field and exactly those methods). Another builds probe files that try direct writes, which must fail to compile, beside one that reads through the view and must compile. A third holds a write through `reflect` alone, which compiles, to the import test's refusal. This is how rustc shares its interned `&'tcx List<T>` and how Go shares a `string` or a `unique.Handle`: the shared value's type has no operation that writes it. The checker side, that nothing writes an interned label after the row is interned, is held by convention, and the window's verifier checks every interned row's labels are unchanged when it closes. It returns the plans and its diagnostics in its own buffers. The budgets above, and the property test below, measure this phase's window; preparation has the bound just described.
    - *Commit* runs after the window: the checker appends the analysis diagnostics in report order and stores the plans.

    Prior art scopes diagnostics the same way but stops short of isolation:
    - rustc's query providers still hold the session's diagnostic context. What the query system separates is the record: diagnostics emitted inside a query are stored as side effects of its dependency node and replayed when the cached result is reused.
    - salsa's tracked functions push values to accumulators, and the caller reads them after the query. This is the closest match to Analyse returning diagnostics and Commit publishing them.
    - Gleam's module analysis collects errors in a per-module `Problems` value and returns them to the caller. Its warnings go to an emitter passed into the analysis.
    - MoonBit's checker records into per-scope mutable collectors (`Local_diagnostics.t`). These are merged into the global collector (`add_to_global`, `merge`), which the driver checks after the pass.
    - Elixir's `Code.with_diagnostics` captures a module's diagnostics in a process-local buffer and returns them beside the result.

    None of them meters bytes per phase or enforces the boundary with a package import rule. Here, the split is what lets every allocation in the window be attributed to the analysis.

  Transition IDs are positional (`<declaration ordinal>:transition:<index>`), so the machine's source name is stored once, in the plan. Functions, enums and the output type bound by several declarations are projected once per module, and their rows are shared across plans. A projected row's ID is the canonical ID retained when the row was interned, so its labels are neither copied nor rehashed. The fields or variants of a data type are resolved once per module, so an application's template is instantiated once however many declarations reach it. Transitions are deduplicated by narrowing and helper ordinals, never by identifier text.

  A property test generates adversarial machines and checks that each module's analysis phase allocates at most 512 bytes and 8 allocations per credited unit. Accepted charges are credited in full; a refused charge only up to the room it found plus one, so an allocation made before a refusal is measured against what the analysis could afford, not what it asked for. It is a sampling property: it finds an escaping allocation wherever the generator reaches. The generator draws wide enums, long names, deep and fanned-out helpers, wide rows, many declarations and deep payloads. It also draws long statement lists after a refusal, long failure labels, generic payload layouts, structured generic arguments across many fields, nested recipe outputs, zero-transition failing bodies, many unrelated records and explicit generic initial values. It also draws checker state before the machines: ordinary diagnostics, and every checker arena, the diagnostics and the intern maps put at capacity as the window opens and verified unchanged when it closes. It also draws data every declaration shares, with 256 declarations: a record of up to 2,000 records reached from each state and event, and an effectful initial raising up to 5,000 errors. What those axes add to preparation is held to the preparation bound of what they add, against the same shape with each drawn axis one wide, because a large unrelated source term would otherwise excuse a declaration repeating work over the shared data; restoring either round-5 repetition fails the default seeds. The sweep measures one generated shape per seed. Seeds 1 to 64 run as four top-level tests of 16 seeds, so the gate can run them in separate shards, and each block must include a module with plans and one refused for its budget. `TestMachineAllocationSweepDeep` runs a deeper sweep with `-machine.seeds=N` (from `-machine.seed`, default 65). The generator caps a source at 128 MiB by cutting its long names to a quarter, then its declarations, until it fits; 18 of seeds 1 to 1,000 drew more (none of 1 to 64), up to 455 MB. The cap bounds a seed's memory, not the checker's time: seed 486, cut to 114 MB, still spends minutes in ordinary checking before analysis begins. For every shape that publishes a plan, it also measures what the plans add to `CheckResponse`, machine inspection and the `machine` graph view against the same bound. Each boundary runs on a fresh compile, and each identity fixture is built outside the measured window.

  The graph view's units include the graph work its own budget charged: the charged work of a published view, the limit for a work-limit refusal, and otherwise the work of the built facts, read from the same view with its size limits lifted. The round-4 counterexamples are fixed cases of the property test. Later counterexamples, including every reviewer probe, are in-tree cases (`machines_review_cases_test.go`, `machines_boundaries_test.go`, `machines_window_test.go`). The round-4 refusal case, a 40 MiB machine name quoted whole in its EF142, allocated 83.9 MB for 65,541 units. On their previous implementations, the round-4 cases allocate 50,000 to 170,000 bytes per charged unit, the round-5 cases 9,000 to 12,000, the template-argument and nested-display cases 600 to 1,800, and the many-records and explicit-initial cases 4,500 to 750,000. A plan's graph node copies a constant amount per plan and per bound function (its facts, values and function records), sized once; the declaration's fixed charge pays for it, so a plan with no transitions stays within the bound.

  The graph view sizes its response before validating it. Validation resolves references over the typed view by its JSON field names, so neither serialises it. Resolving a data declaration's qualifier compares names in place, so validation allocates nothing per declaration. Counting a response's strings reads each struct type's visible fields from a per-type list, so it allocates nothing per field visited. Seed 1025, where an explicit generic initial publishes a deep value, is a fixed case. The one type that marshals itself, `ValueType`, publishes ownership facts that carry no checked reference key; a test pins that, and a differential test compares the walk with the earlier JSON round trip.

  Exhausting any limit refuses the declaration; no cutoff ever classifies uninspected code or data as admitted. Once a declaration is refused, EF142 is the only analysis diagnostic reported for it, because a check the budget cut short is not evidence of a contract violation; EF142 already rejects the source. Checker diagnostics from preparing it, such as an ill-typed `initial`, are reported as for any expression. Once the shared budget is exhausted, later declarations are not analysed. The `machine` graph view charges its node and edge identities and labels by bytes as well as by count, and stops at its first refused admission.
- **Formatter.** Machine syntax is admitted from formatter identity `ergo/formatter-13`. The current identity, `ergo/formatter-16`, admits it alongside typed endpoint declarations and decision forms; formatter-16 prints a form like `run`, with one space before its operand, and keeps the operand on the word's line.
- **Canonical plan.** Each declaration is published under `machines` in `ergo check` and `project.check` and through `ergo inspect FILE Machine` and `code.inspect`, only for fully checked source. The plan carries:
  - a stable `machine:<module>:<name>` identity, the declaration's ordinal, and the state, event and output identities;
  - the initial variant;
  - the bound functions with kind (pure or effect), failures, services and full contract, plus per-role terminal-failure and requirement contributions;
  - possible transitions as from-set × trigger-set → decision, each with a `literal`, `current` or `conservative` target precision, a guard flag, a helper chain and a source span;
  - per-state `initial` and `enterable` facts, and whether some decision can finish;
  - the evidence label `checked-static-machine-plan` and the plan's limitations.

  `enterable` is a sound over-approximation from `initial` over `enter`, `stay` and conservative edges. It is published as a fact, not a diagnostic, and it is not a reachability proof. Decisions the walk cannot classify become `any` transitions with conservative targets. `ergo graph --kind machine` and MCP `project.graph` project the same plan as a GraphViewV1 ([tooling](../tooling.md#graph-views)). Planning never evaluates a step: a step that recurses forever still plans, as one conservative `any` transition.
- **Emission.** The declaration emits nothing. Step functions are ordinary functions that run on Go and JS, as [`machine-search.ef`](../../examples/machine-search.ef) and [`machine-breaker.ef`](../../examples/machine-breaker.ef) show: a pure step, and an effectful step with a declared failure and a service.

- *#11 and #47.* `Actor<M>`, spawn charging of the declaration's rows, send, call and result operations, terminal failures reaching waiting observations, portable payload ownership in place of the conservative check, and runtime snapshots.

- *Delivery items 3 and 4 and the measurements in item 2.* Runtime execution, frontend, emission and adversarial cost measurements (benchmarks-last), request-owned HTTP cancellation, and a non-server actor.

Prior art for the decisions here:

- *Anchoring the current state on the first parameter.* gen_statem passes the state as a fixed callback argument, and effect-machine's handlers receive the state explicitly. The spike's "only S-typed parameter" heuristic is rejected.
- *A static `stay` rule with a dynamic fallback.* XState v6 uses targetless transitions, and gen_statem's `keep_state` and effect-machine compare at runtime. Rust typestate makes illegal states unrepresentable only for statically known states; Effra checks the narrowed cases and leaves dynamic values to the runtime defect.
- *Context-sensitive recursion.* Reusing a body's result only under a covering context is summary reuse as in context-sensitive abstract interpretation and k-CFA, with the narrowing as the context. Erlang's Dialyzer uses success typings, which are deliberately unsound in the other direction: they report only certain failures. `gen_statem` makes no static check. TypeScript's control-flow narrowing does not cross calls, so a narrowed subject passed to a recursive call is not narrowed in the callee. Effra carries the narrowing into the call because the `stay` rule must hold wherever the step body runs.
- *Refusing statechart words.* XState's hierarchy, parallel regions, history and delays stay out of the first profile, as do gen_statem's `postpone` and event and state time-outs.

### Comparison with Erlang `gen_statem`

`gen_statem` is the closest runtime model and a standing comparison. Sources are pinned at OTP `516126e9` (`OTP-29.1.1-1070`), `lib/stdlib/src/gen_statem.erl`. Elixir has no machine abstraction in core; it uses `:gen_statem` directly, and its Logger translates `gen_statem` terminations (`lib/logger/lib/logger/translator.ex`, elixir `91ee75b`).

| `gen_statem` | Effra machine | Difference |
| --- | --- | --- |
| Callback mode `state_functions`: the state is an atom name with separate `Data` | Tag of the `S` enum plus its payload | Effra's tag plays the state name and the payload plays `Data`; one closed enum keeps both checked |
| Callback mode `handle_event_function`: the state is any term | One `step` function matching `state, event` | The match is checked for exhaustiveness (EF117); there is no catch-all fallback |
| A *state change* is `NextState =/= CurrentState`, compared at runtime | `enter` always re-enters; `stay` keeps the entry | Effra makes the choice explicit instead of comparing terms. `enter` to the same tag re-enters, which `gen_statem` does only through `repeat_state` |
| `keep_state` / `keep_state_and_data` | `stay next` with the same tag | `gen_statem` cannot be wrong, since it never changes the state. Effra lets `stay` replace the payload, so it must check the tag: statically under narrowing (EF139), by runtime defect otherwise |
| `repeat_state`: repeat the state enter call without a state change | `enter` to the same tag | Effra's re-entry also cleans up the old entry's work. `repeat_state` keeps a running state time-out, because it is not a state change |
| State enter calls (`state_enter`): run on every state change, limited to `enter_action()` (no state change, only time-outs, replies and hibernate) | `enter` returns an optional deferred `Outcome`, and only `complete` decides | Both forbid entry code from changing state directly. Effra's `enter` is not admitted yet (EF141) |
| `postpone`: retry the event after the next state change | Not supported; `ignore` or `reject` | Postponement needs a runtime queue policy (#11) |
| `event_timeout` (cancelled by any event), `state_timeout` (cancelled by a state change), generic time-outs | Not supported as syntax; timed work belongs to entry work | An entry-owned timer is cancelled when its entry ends. That matches `state_timeout`, except that a same-tag `enter` also restarts it |
| Next state chosen by returning a term; the engine has no static plan | Checked plan with possible transitions | Inspection has no `gen_statem` counterpart; `sys:get_state` is a runtime snapshot |

## Decisions

Status: implemented (M1 of [statecharts composition](../research/statecharts-composition-and-evidence.md#3-decision-syntax), 2026-10-12). Decisions are syntax. Under the owner direction of 2026-10-09, checker-known constructs are syntax rather than special-cased library items. The bundled `Step` enum of `ergo/machines`, which the checker recognised by template identity, is removed together with that module.

~~~rust
fn searchStep(state: Query, event: QueryEvent) -> decision<Query, i64> {
    match state, event {
        Query.Idle | Query.Ready | Query.Failed, QueryEvent.Submit { text } => enter loading(text)
        Query.Loading { text: current }, QueryEvent.Submit { text } => if text == current {
            stay state
        } else {
            enter loading(text)
        }
        Query.Idle | Query.Loading, QueryEvent.Reload => ignore
        Query.Ready { hits }, QueryEvent.Close => done hits
        Query.Idle | Query.Loading | Query.Failed, QueryEvent.Close => reject
        // …
    }
}

fn describe(decision: decision<Query, i64>) -> string {
    match decision {
        enter next => "enter " + label(next)
        stay next => "stay " + label(next)
        ignore | reject => "unchanged"
        done hits => "done"
    }
}
~~~

- **Type.** `decision<S, O>` is a predeclared generic type, like Go's predeclared `error`. It is a closed enum with the variants `enter { next: S }`, `stay { next: S }`, `ignore`, `reject` and `done { output: O }`, whose names no source declaration can spell. It is in every module's type scope when the program names it, and only there: as a value, `decision` resolves as an ordinary name, so a function, service, provider, parameter or local named `decision` keeps working next to a step that returns `decision<S, O>` (the examples name a parameter `decision`). `decision` is not reserved, and a source record or enum named `decision` shadows the predeclared type, as a local declaration shadows a Go predeclared identifier.
- **Forms.** `enter e`, `stay e`, `ignore`, `reject` and `done e` are prefix expressions like `run e`: the operand binds tighter than any binary operator, so `done a + b` is `(done a) + b`; write `done (a + b)`. `done` takes an operand exactly when the next token is on the same line and can start an expression (a name other than `else`, a literal, `(` or `-`). An arm separator (`,`, a newline or `}`) ends a bare `done`, so `E.Ping => done, E.Pong => stay s` and `E.Ping => done n, E.Pong => stay s` both parse as written, in a product match too. This is Rust-style expression-start detection with a Go-like newline boundary (automatic semicolon insertion), and it needs no lookahead: in `E.Ping => done E.Pong => stay s` the operand is `E.Pong`. The repair is diagnostic recovery and leaves that rule unchanged. When a `done` that took an operand is followed by `=>` or by the `|` of an or-pattern, or when a product arm that starts on the line where the previous arm ended with `done X,` has fewer cells than the match has subjects, the match is EF002 with the repair (`end a bare done with , or start the next arm on a new line`) instead of the parse or arity error it would otherwise raise. The formatter keeps the separator, so formatting never changes which arm a `done` ends. Bare `done` is admitted only when `O` is `void`. A form is typed against the declared result of its enclosing function, which must be `decision<S, O>`. Effra has no annotated `let`, so that result is the only expected type; inside the function a form may appear anywhere, including a `let` initializer and a helper argument. The operand is a pure value that must be assignable to `S` (`enter`, `stay`) or `O` (`done`). An Effect recipe operand is refused (EF106, `execute an Effect with run first`) even where `O` names a recipe type, a deliberately narrower rule than ordinary generic data, which may hold a lazy recipe: machine payloads may not carry recipes (the non-portable payload check of the first profile), and entry work belongs to the `enter` binding.
- **Patterns.** The same words are patterns: `enter next`, `stay next`, `done output` and bare `done` bind the payload or `_`; `ignore` and `reject` take no binder. They combine with `|` and other subjects, and coverage (EF117) names a missing decision by its word, for example `missing match arm for done`.
- **No construction through the type.** When no value named `decision` is in scope, `decision(x)`, `decision.enter(x)`, `decision.enter { next: x }` and the dotted pattern `decision.enter { next }` are refused (EF143) instead of reported as unknown names, so decision syntax is the only way to write or match one. The refusal runs only after ordinary value resolution has found nothing.
- **Reserved words.** `enter`, `stay`, `ignore`, `reject` and `done` are reserved where a name can start an expression or bind a local. As a declaration, parameter or local name each is an EF002 parse diagnostic that names its decision form (``done is reserved for the decision form `done value```). A label never starts an expression, so the words stay legal as explicit field labels: record and variant field declarations in braces or parentheses (`Finished(done: bool)`), constructor `done: value` in braces or as a named argument (`Todo(done: true)`), pattern `done: binder` and member access `todo.done`. A derived codec therefore carries wire keys such as `"done"`, as Rust raw identifiers, Swift backticks and TypeScript property names allow. Only the shorthand `{ done }`, which reads or binds a local of that name, is EF002, with the explicit spelling as its repair. The words also stay legal as qualified host members and as the machine binding word `enter`, which the declaration parser reads by position.
- **Diagnostics.** EF143 (new) refuses a form where no decision is expected: in a function that does not return `decision<S, O>` or outside a function. It refuses any non-final statement whose checked value is a decision, whatever its syntax: a bare form, an `if` or `match` whose arms decide, or a helper call. A decision is a value, never an early exit, so `if bad { reject } else { … }` followed by more statements would otherwise read as a return and be silently dropped. A `let` binding or an argument consumes the value and stays legal. EF143 also refuses construction through the type. An operand of the wrong type and a bare `done` with a non-void output are EF106 type mismatches. EF139, EF140, EF141 and EF142 keep their meanings; their messages now spell decisions as words (`` `stay` keeps the current entry … use `enter` ``, ``must return decision<State, Output>``). M2's region-provenance diagnostic takes the next free code.
- **Region updates are not admitted.** `stay V { field <- d }` is EF002 (`region updates … are not admitted`). The `<-` is contextual: it is read only right after a constructor field name, so `x<-1` in a block and `if x<-1 { … }` stay comparisons with a negation.
- **Plan and provider.** Analysis recognises a form by its syntax: the lowered expression kind `decision`, and an application of the predeclared template, which the checker marks on the prepared type node. No checker branch keys on a library declaration's identity or name. Plans carry the same typed transition data as before, under one word per concept: the transition kinds are the source words `enter`, `stay`, `ignore`, `reject` and `done`, plus the conservative `any`, and graph edge labels read the same (`enter: Submit`). The design's plan kind `go` was renamed with the form before any plan was published, as `gen_statem` uses one vocabulary in source and in its transitions. A transition's span is its decision word. The `decision` declaration replaces `Step` in a program's declaration and type facts (`template:ergo/language:predeclared:decision`, source `language:decision`).
- **Emission.** A form lowers as a construction of the template's variant on both targets, with the general generic-enum layout, so steps run on Go and JS as before. A flat representation is M6's measurement, not claimed here.
- **Migration.** `import Machines "ergo/machines"` is the ordinary unknown-bundled-module diagnostic (EF126), and its help names the replacement. Rewrite `Machines.Step<S, O>` as `decision<S, O>`, `.Go(x)` as `enter x`, `.Stay(x)` as `stay x`, `.Ignore {}` as `ignore`, `.Reject {}` as `reject`, `.Done(x)` as `done x`, and the patterns `Machines.Step.Go { next }` as `enter next`. A user enum named `Step` is ordinary data.

### Why `enter`, not `go`

The design proposed `go e`. The readability rule of 2026-10-12 says that no well-known keyword is reused with a different meaning. To Go readers, `go f(x)` starts a goroutine, and Effra itself already uses `go` for the Go target (`import go`, `--target go`). A transition is not concurrency, so `go` fails the rule. The form is spelled `enter`:

- It names the lifecycle exactly. The form closes the current entry and starts a new one, even for the same tag, and the opposite form is `stay`. Harel 1987 and STATEMATE speak of *entering* a state, SCXML runs `<onentry>` in `enterStates`, XState's `reenter: true` marks the same re-entry on a self-transition, gen_statem runs a state enter call on each state change and repeats it with `repeat_state`, and UML has entry behavior.
- It is not a keyword in Go, TypeScript, Rust, Python, Elixir, Erlang, MoonBit, Gleam or ReScript.
- It agrees with the machine's `enter` binding: the binding names the function that runs when a state is entered, and the form requests that entry.

Rejected: `next`, a common identifier and a loop keyword in Ruby and Perl; `become`, reserved in Rust for tail calls and an Akka actor method with another meaning; `target`, which is Effra's compile-target word; `goto`, a jump in Go and C. `stay`, `ignore`, `reject` and `done` keep the design's spelling: none is a keyword in those languages with another meaning (`done` closes a loop only in POSIX shell). Plans publish `enter` too, so source, plan, graph and provider share one word.

SCXML gives the formal names: a targetless transition keeps the configuration, which is `stay`, and an external self-transition exits and re-enters its source, which is a same-tag `enter`.

### Closed protocol

- *Closed set.* The decisions are a closed set between the checker and every provider, so transitions are provable and every provider agrees on their meaning. Providers match the decisions as data and never extend them, the way `gen_statem` interprets ordinary return tuples at runtime (`state_callback_result`, `lib/stdlib/src/gen_statem.erl` at OTP `516126e9`; Elixir calls the same `:gen_statem`). Provider-specific behaviour, such as `postpone` or `state_timeout` and `event_timeout` (refused today with EF002), goes through services in the step's `uses` row or through `Output`. A new core decision is a versioned language change.
- *Rejected: an open, user-defined decision set.* Each provider would then decide what a decision means, losing the static `stay` check, the canonical plan and portability across providers. That is the free-monad interpreter model of Scala and Haskell, where the interpreter, not the checker, owns meaning. [Users write their own runtimes](machine-provider-contract.md) as providers over the closed set.

## Prior art: Erlang/OTP `gen_statem`

At OTP `516126e9` ([PRIOR_ART](../../PRIOR_ART.md#elixir-with-erlangotp)), `lib/stdlib/src/gen_statem.erl` runs state enter calls on every state change, meaning the new state term differs from the old (`L735-L764`). `keep_state` changes only data, and `repeat_state` repeats the enter call without a state change (`L1367-L1380`). A state change cancels a `state_timeout` (`L812-L817`), and `postpone` retries an event after the next state change (`L848-L857`). An enter call that returns a different state crashes the server at run time (`L1606-L1619`).

Effra adapts this lifecycle and removes the run-time failure mode. `enter` to the same tag re-enters like `repeat_state`, and entry-owned work is cancelled by `enter` as a `state_timeout` is by a state change. Because `gen_statem` compares whole state terms, changing a payload carried in the state is a state change; `stay` instead updates payload data while keeping the entry, under a statically checked same-tag rule. `enter` is a pure function returning optional work rather than a decision, so changing state from an entry is unrepresentable instead of a crash. Postponement stays outside the first profile.

## Statecharts composition and decision syntax (2026-10-09)

Status: M1 (decision syntax) is implemented, with `enter` in place of the proposed `go` (see [Decisions](#decisions)); the rest is proposed, not implemented. The evidence, probes and rejected alternatives are in [statecharts composition and evidence](../research/statecharts-composition-and-evidence.md), which compares Harel 1987, STATEMATE, SCXML, XState v6 (`ac890f2a3`), `gen_statem` and MoonBit.

- **Owner direction, 2026-10-09.** For machines and for language constructs generally, syntax is preferred over a library item that the checker special-cases.
- **Hierarchy and history stay ordinary data.** A variant carries its child state, and outer match arms cover every child configuration. History is a remembered child value restored by a later `enter`. No `history` declaration is added. The statechart words remain EF002 until a ticket admits them.
- **Orthogonal regions keep their state as data.** The declaration gains `region V.field M` bindings to separately declared child machines, with `field <- decision` updates written directly in a `stay` argument. Every region-owning `stay` must show each region's decision (or be `stay state`). Every decision that can reach a region-owning parent must come from a checked source, so service results and decision parameters are refused there. `done` never reaches a region. Regions give per-region entries and epochs, checked delegation and factored plan facts. Composition alone is not enough: it accepts a region change lifted as a parent `stay`, so stale region work can still complete, and it cannot express SCXML exit/entry order.
- **`Step` gave way to decision syntax (M1, implemented).** The predeclared `decision<S, O>` type replaced the bundled `Step` enum, which the checker recognised by template identity. Its forms are `enter e`, `stay e`, `ignore`, `reject` and `done e`, written as expressions and as patterns; the design's `go` became `enter` under the readability rule. Plan facts carry the same data, and the plan kind is `enter`, as in source. EF139 follows the `stay` form.
- **Running identity.** The spawn boundary mints a start token and checks the returned `Running`'s plan id, revision and token before it produces `Actor<M>`, because declarations with the same shape share a `Running` type.
- **Laws.** Decision, region and history laws extend the [provider obligations](machine-provider-contract.md#provider-obligations) with the existing lawful-runtime rows. They add no new vocabulary.
