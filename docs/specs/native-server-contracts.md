# Native codecs, HTTP and unary RPC

Status: implementation authorized by the owner on 2026-10-06 as the prerequisite for actual Effect framework server comparisons. This extends the [standard library direction](../standard-library.md) and [matched server benchmarks](server-benchmarks.md). It does not claim full Effect API parity.

## Outcome

An ordinary `.ef` application declares nominal domain data and typed effect handlers once, then exposes validated HTTP endpoints or unary RPC methods from bundled library contracts. The Go target produces a standalone executable. Canonical CLI/MCP inspection explains codecs, handler rows, transport contracts and their dependencies. Unsupported targets and protocol modes diagnose or reject explicitly.

`Http.listen(address, limits, handler)` is the sole builtin HTTP server operation on Go and server JavaScript; the raw path-to-string `Http.serve` and the `Handler` shorthand were retired without a facade (EF102). Framework completion requires reusable contracts and real source programs, not raw JSON passthrough, duplicated handwritten signatures or compiler branches for benchmark endpoints.

## Shared language and library contracts

- Introduce a versioned bundled interface boundary with package-qualified identity. Load only referenced contracts; include interface versions in semantic revisions. An initial bundled-only loader must state that user package resolution is unavailable.
- New bundled modules use explicit imports; retain only a finite compatibility prelude for existing builtins. Stored interface ownership summaries have their own versioned lossless representation for parameter/call relations, potential ownership and trusted host behavior. Inspection JSON deliberately omits internal summary fields and cannot be reloaded as executable ownership evidence.
- Select reachable implementation modules independently from interface availability. Follow the [small executable contract](binary-reachability.md): unused HTTP/RPC/codecs and their initialization must stay out; fluent spelling must not retain an entire library API. Codec/HTTP/RPC acceptance includes extending the size/dependency fixture matrix.
- Represent named function values through one structural type model: parameter types, success type, effect status, explicit failure and service rows. Check passing and invoking functions through typed parameters. Preserve lexical captures separately from invocation ownership. HTTP handlers use this model: `Http.listen` takes an ordinary `HttpHandler` function value whose failure and service rows are checked like any other callable's. (The special opaque `Handler` representation this item originally replaced was removed with `Http.serve`.)
- Support checked type applications needed by shipped witness/container interfaces, including `Codec<T>`. Resolve operations from the versioned contract rather than endpoint-specific checker branches. The [language abstraction contract](language-abstractions.md) requires explicit finite row parameters alongside function values, so helpers retain their argument contracts. General user-defined generics, lambdas and complex polymorphic row inference may remain separately gated with diagnostics; do not confuse explicit row parameters with unrestricted inference.
- Keep rows intact through endpoint registration and composition. Transport provision discharges transport authority, while domain services remain required. Only explicitly mapped typed failures become declared transport responses; defects and interruption remain distinct.
- Canonical inspection must expose these contracts consistently through check/inspect/query/graph and MCP. No separate tool inference from generated host source.

## Codec contract

A codec is a typed decode/encode witness with distinct wire and domain types. Rust-style structural derivation from canonical primitive and nominal data declarations is its starting point; Effect-style transformations are part of the required model, not a later substitute for it (owner clarification, 2026-10-06). Compiler-generated adapters connect source identity to reusable parsing, validation and encoding modules. The compiler does not embed whole runtime algorithms in emitted strings.

Keep three composable concerns: derive structural representation, validate/refine values, and transform between representations. A codec can decode a wire string into a nominal identifier or a transport record into a richer ADT; encoding has its own transformation and validation. Pure functions and checked effect functions use the same function/row model. Canonical inspection exposes domain type, wire type, decode failures/services and encode failures/services separately, including their contribution paths. A convenient public spelling must not erase any of these contracts. Structural derivation itself introduces no service requirements.

Composition combines the selected direction's failures and requirements. A decode-only service does not become an encoding requirement merely because both directions share one witness. Transformations remain lazy until the boundary executes them, run in its owning scope, and preserve interruption/defects distinctly from expected validation errors. Decode cancellation and failed encode cleanup must never publish a success response. User transformations are checked source functions, not arbitrary compile-time procedural macros.

Keeping named transformation failures is an Effra extension: pinned Effect's SchemaGetter effect callback fails with SchemaIssue.Issue, and Schema.decodeUnknownEffect exposes SchemaError. Effra must distinguish malformed representation/validation from a declared service failure encountered during transformation. A service outage is not automatically bad input. Convenience annotations such as Codec<T> must preserve the actual witness's wire type and directional rows through the common checked representation; reject an annotation or unsupported placement that would erase them.

Go-like surface decision after independent counsel: opt-in structural derivation should be concise, with the direction contracts carried by ordinary named decode/encode functions and exposed in full by inspection. First-profile renames, defaults and migrations use explicit wire types/functions rather than a growing field-attribute language. Keep named codec values explicit and allow several witnesses for one domain type: API versions and storage formats must not require nominal wrapper proliferation or global implicit witness selection. A default derived witness is a convenience, not a one-codec-per-type coherence restriction. Do not overload provider `impl` or introduce pure-function `raises` semantics merely to spell codec customization; use the common admitted function/recipe/Result contracts. Structural derivation is a compiler-special fulfilment that no library could write, so it stays the visible `derive` construct rather than an ordinary-looking library call. Every derive states both plan bounds, `maxBodyBytes` and `maxDepth`; there is no default budget.

Derivation and format policy are separate. A profile chooses structural JSON rules; the matched Effect comparator currently ignores excess properties and stops at the first issue. A stricter profile requires its own concrete consumer, name and tests and is deferred from the first slice. No counsel recommendation for strict defaults silently changes the comparator contract. A derived parent containing custom field transformations inherits their actual behavior; it cannot claim a structural inverse law just because its outer record was derived.

Do not assume every codec is a bijection. Specify identity round trips only for representations that support them; normalizing or lossy transformations need explicit canonicalization/equivalence laws and encode rejection where appropriate. Defaults, field renames and version migrations are explicit policy. Derivation cannot silently make a persisted wire-format change safe.

The first profile admits strings, booleans, `void` where explicitly represented, full-range i64 via decimal strings, nested records, closed payload enums and declared payload failures. File, Fiber, providers, functions and effect recipes cannot cross this boundary. Recursive layouts remain unsupported. Plans must share canonical type DAG nodes; repeated substructure must not enumerate exponentially many paths.

Before accepting a codec implementation, record executable policy vectors for required and excess fields, null, duplicate keys, invalid UTF-8, unknown discriminators, integer range and spelling, escaping, body size and nesting limits. Go and the pinned Effect Schema comparator must apply the same profile. Strictness that the host parser cannot prove must be supplied by a shared admission layer or excluded explicitly from the accepted contract; do not silently label it validated.

Decode failure includes bounded field-path and reason information without dumping arbitrary input. The HTTP malformed-input profile returns an empty 400 body; retain details in the cause/inspection rather than inventing a different wire response. Encoding has an honest failure contract. Parsing occurs once per boundary. Stable field/discriminator order is an Effra guarantee: pinned Schema explicitly does not guarantee property order. Capture comparator output bytes empirically before admitting matched wire vectors.

Encoding is bounded by the plan's `maxBodyBytes`, as decoding is. Encoder memory is O(`maxBodyBytes`), never O(input): each engine reserves every piece against the remaining allowance before building it, so no output piece or body beyond the allowance is constructed or published, and an oversized value fails with `body-too-large` rather than a truncated body. Encode transformations run as the writer reaches them and build no prepared tree; after the allowance is exceeded the remaining transformations still run without writing, so a shared value that expands far beyond the budget retains nothing more (`TestCodecEncodeRetainsNoPreparedTree`, `TestCodecJSEngineEncodeRetainsNoPreparedTree`). Time remains proportional to the transformations the value requires, as in Effect's `Schema.encode`, which runs every transformation before serializing. Fixed-size scratch, such as an i64 spelling or an escape, and host buffer growth within a constant factor of the allowance stay within this bound. Failure precedence is identical on every target: failures surface in encode order (declared field order, a union's discriminator first), and a string's Unicode is validated before any of its bytes are written, so ill-formed text reports `invalid-unicode` even when its encoding would also exceed the remaining allowance.

The i64 profile applies an explicit signed 64-bit range check to both cohorts. Pinned BigIntFromString is unbounded; its decimal spelling permits leading zeros and negative zero, which normalize on encoding. Range rejection is additional matched work, not inherited upstream behavior. Duplicate-key, invalid-UTF-8, escaping and depth/size vectors need local execution; source inspection alone is insufficient where upstream tests do not assert them.

Acceptance: two unrelated nominal records, a nested payload enum and a payload failure all round-trip or reject through public source programs; negative cases reject malformed or unsupported values. A payload codec specific to the benchmark does not meet this contract.

Transformation acceptance adds a pure string-to-nominal conversion, an explicit normalizing codec, and an effectful conversion with different decode/encode requirements. Test nested composition paths, encode-side rejection, missing service and undeclared failure diagnostics, cancellation with completed cleanup, direction-specific inspection and Go/JS parity. Exercise the same derived/transformed witness through an HTTP boundary and a non-server configuration or stored-data example. Do not add unrelated external work to a benchmark cohort; matched codecs must perform equivalent validation and conversion.

Implementation status (2026-10-09): transformed witnesses are implemented on Go and JS ([bundled modules](../bundled-modules.md#transformed-witnesses)). `decode:`/`encode:` name ordinary pure or effect functions over a structurally derived representation (Serde `try_from`/`into`, Effect `Schema.decodeTo(to, { decode, encode })`), and `with` composes transformed witnesses explicitly. Evidence: `examples/codec-transforms.ef` (pure nominal, normalizing, refining and effectful witnesses, nested composition, encode-side rejection, a stored-data and a configuration caller) run by `ef test` on both targets; a cancellation fixture with an uninterrupted control; compiler refusals and caller row diagnostics; CLI/MCP inspection parity; and `conformance/codecs/json-transform-vectors.json` executed on both engines and pinned Effect Schema. The HTTP-boundary clause depends on typed endpoints and is tracked with the HTTP contract below.

Recorded decisions (2026-10-09):

- Structure first. Decoding validates the whole representation before running any decode transformation; encoding runs every encode transformation before writing bounded output. Pinned Schema runs each transformation as soon as its own subtree decodes, so a later malformed field can be preceded by a service call; the transformation vectors record that executed difference. Rationale: malformed input never reaches a service (NORTH_STAR: explicit contracts, a service outage is not bad input), and both engines stay synchronous and effect-free, driven by caller-supplied steps.
- Explicit selection. A parent lists transformed witnesses with `with`; there is no global, implicit or type-class witness (rejected per PRIOR_ARTS: global witness uniqueness), and a listed witness that never occurs is refused. A witness's representation uses only its own `with` list, so plans are keyed by type and scope and stay a shared DAG.
- Unchanged failures. A transformation's typed failure, defect or interruption leaves the engine unchanged rather than as a structural failure, so it carries no codec path; inspection reports the first plan path at which each transformation applies. Wrapping it in a path-carrying issue (pinned Schema's `SchemaIssue`) was rejected because it would erase the declared failure type.
- Directions are separate functions with one parameter each. Field-level attributes, a single bidirectional function and procedural macros were rejected as in the Go-like surface decision above.

## HTTP contract

Separate managed HTTP transport from typed endpoint composition. Transport exposes method/path, buffered request bodies with a required byte budget, response status/headers/body, and explicit server limits. The body budget is finite today; `unbounded` is pending a runtime change and its justifier rule ([budget choices](standard-library-capabilities.md#budget-choices)). Endpoints declare method/path, input codec, success codec/status and each typed failure codec/status, and bind a typed effect handler. Route matching and response policy belong to reusable library code.

The first profile is HTTP/1.1 buffered JSON with exact static routes. It specifies success and failure responses plus 400 malformed input, 404 unknown route, 413 excessive body, 415 unsupported content type and 500 defect behavior. Wrong-method handling is an explicit endpoint profile choice: the pinned Effect framework comparator returns404, so its matched native cohort uses404 rather than silently comparing it with405. The shared wire corpus records exact status/body/content-type behavior. Match limits for Content-Length and chunked bodies. Explicit read-header/body/idle limits and admission bounds must be recorded with fixtures.

Server interruption returns 503 only if a response remains possible after owned cleanup. A disconnected client receives no further bytes; upstream's client-abort 499 is an observation, not a promised delivered response. Body limits are explicitly configured in every cohort: pinned Effect has no default MaxBodySize. Record its overflow behavior before applying a shared 413 admission profile.

Every request has an owning scope linked to client disconnect and server cancellation. Shutdown stops admission, cancels active handlers, waits for children and finalizers, and only then reports completion. Response publication occurs after owned handler and encoding cleanup at the agreed boundary; cleanup defects cannot become success. Readiness and lifecycle receipts use explicit host facilities rather than sleep-based startup assumptions or workload-specific magic routes.

The agreed boundary is the owned application request scope, including handler and encoding resources. Close-before-publication is an Effra guarantee, not default Effect HTTP/RPC fidelity: at the pin, outer transport code can publish before closing its request scope. Matched cohorts must use an equivalent explicitly completed inner application scope and prove ordering with client observation; otherwise mark the case different and ineligible for matched scoring. Success-encoder failure is a generic 500 in this profile; pinned HttpApiSchemaError can render 400 for a response-body encoding error. Record that difference explicitly or adapt both comparators to an equivalent policy before including that path in scored workloads.

Endpoint composition includes input decoding, handler execution and success encoding contracts, not just the handler's rows. Structural request validation follows the selected malformed-input profile. Named transformation failures must be explicitly recovered or included in the endpoint's typed response mapping; an unmapped failure is a source diagnostic. Retain requirements for every reachable response encoder. Error-response encoding is a terminal boundary with a declared fail-closed transport policy: preserve its cause and completed cleanup, emit the profile's bounded generic500 when a response remains possible, or close after cancellation. Do not recursively map a failed error encoder through itself, retry transformations, or silently turn a named failure into a defect. Inspection distinguishes primary execution rows from this terminal encoding policy.

Implementation status (2026-10-07): the codec-independent transport slice is implemented as `Http.listen` with builtin `HttpRequest`/`HttpReply`/`HttpLimits` records on Go and JS ([runtime contract](../runtime.md#managed-transport)). It covers 400/404/413/415/500/503, Content-Length and chunked bounds, read-header/body/idle and admission limits, disconnect and shutdown cancellation, publication after request-scope cleanup, admission held until each response is handed to the OS, a shared Content-Type value policy, and shutdown that joins every request scope before a separate drain phase aborts stalled response writes after `idleMillis`. It is the only builtin server operation: the raw `Http.serve` control and its `Handler` shorthand were retired the same day, and `examples/http.ef` now runs on it. It represents only Content-Type, not general headers or query. Typed endpoints, codecs, the route table and the shared wire corpus build on it.

Implementation status (2026-10-09, wire corpus): the shared wire corpus lives in `conformance/http/`. Each `*-vectors.json` file names its program, the exact `HttpLimits` that program declares (checked against the source, so a drifted program or vector fails), plain exchanges with exact status/body/content-type and connection close, and lifecycle cases (body read timeout, disconnect releasing admission, a malformed request held open across shutdown, shutdown with active work answering 503 then completing with interruption). The `cmd/ef` process test `TestHTTPWireVectors` executes every file over real sockets on Go, Bun and Node; the transport vectors replace its former inline expectations unchanged.

Acceptance: public `.ef` HTTP application, shared request/response corpus, invalid/oversized input, typed failure, client disconnect and shutdown with active work. No unobserved task remains after the completed shutdown receipt.

Include a decode transformation that raises a service failure: its explicit mapped response differs from malformed input, an omitted mapping diagnoses, and its service remains required through endpoint helpers. Pair a success-encoder failure mapping with a terminal error-encoder failure to prove no success bytes, recursive encoding or lost cause. These extra transformation cases are conformance tests; matched performance fixtures must still execute equivalent work in every cohort.

Implementation status (2026-10-09, typed endpoints): `derive name = Http.endpoint(method:, path:, input:, handler:, output:, status:) raises { Failure: status [failureWitness], ... }` and `derive name = Http.routes(...)` are implemented on Go and JS ([declarations](../bundled-modules.md#failure-witnesses-and-typed-endpoints), [profile](../runtime.md#typed-endpoints)). Evidence: `examples/http-endpoints.ef` (public source; its `ef test` suite runs on both targets), `conformance/http/endpoint-vectors.json` (17 exact wire exchanges on Go, Bun and Node), `TestEndpointRefusals` (36 refusals with positive controls, including the omitted mapping of a decode transformation's service failure and the retained service requirement), `TestEndpointRowsAndInspection`, `TestEndpointRetention`, `TestEndpointTestsPassOnGoAndJS` (a failed failure-body encoding fails with `JsonEncodeFailure` then the mapped failure on both targets) and `TestEndpointFactsMatchAcrossCLIAndMCP`. Not implemented: path parameters, query and header inputs, decoding failure witnesses (a client), streaming, and a pinned Effect `HttpApi` server comparator running the same vectors.

### Typed endpoint decisions (2026-10-09)

- **Declaration form.** Effra has no user generics or row-polymorphic helpers, so a library function cannot type an endpoint over arbitrary witnesses and handlers. An endpoint is therefore a visible `derive` declaration, like a codec witness, whose checker synthesizes one ordinary handler function; the response policy itself is one reusable helper per target, not per-endpoint compiler branches. Prior art: pinned Effect `http-api/HttpApiEndpoint.ts`/`HttpApiGroup.ts` (endpoint values built from schemas, implemented with `HttpApiBuilder.group`), Rust axum handlers typed by extractor traits; both rely on generics Effra lacks.
- **Failure mapping.** Every named failure reachable from the input witness's decode transformations, the handler and the output witness's encode transformations must be mapped (EF107 otherwise); a mapping is a status plus an optional failure witness, like `HttpApiSchema.status(...)` on an error schema. Mapping an unreachable failure is refused (EF138), unlike Effect, which accepts any declared error schema: an Effra mapping is a checked claim about rows. `JsonDecodeFailure`/`JsonEncodeFailure` are profile-owned and unmappable; a handler or transformation raising either must recover it, so at run time each tag has exactly one origin.
- **Failure bodies.** A failure witness encodes `{"_tag": name, ...fields}`, the encoded form of an Effect `Schema.TaggedError`. A failed failure-body encoding is terminal and keeps both causes in order (`Cause.combine` on JS, appended reasons on Go); pinned `HttpApiBuilder` turns the same failure into a defect with `Effect.orDie(encodeError(error))`. Both answer 500; Effra additionally keeps the typed failure observable.
- **Compound causes (2026-10-09 review).** A mapped failure is answered only when it is the whole cause. A compound cause, such as a handler failure beside an unobserved failed child, propagates complete, so the synthesized function's row keeps every mapped failure, the conservative fork rule applied to the boundary; `Http.listen` absorbs it as its generic 500. Effect's `causeResponse` (`unstable/http/HttpServerError.ts`, read in effect-smol `3a1128c7` lines 283-326) instead picks the last respondable `Fail` reason's response and reports the rest of the cause to logging middleware; Effra has no such side channel on a direct call, and choosing one failure's response would drop the others. Plug answers a raised exception by its `plug_status` or 500 (`lib/plug/exceptions.ex:51-52`); a linked task crash takes down the request process, so there is no compound response either. MoonBit raises one error value per call (`json/from_json.mbt:21-28`), so the case does not arise. Evidence: `TestEndpointDirectInvocationKeepsCompoundCauses` (lone and compound controls, Go and JS).
- **Content type.** Input requires media type `application/json`; an absent header reads as JSON, matching `HttpApiBuilder.decodePayload` (`headers["content-type"] ?? "application/json"`). Effect's 415 carries a text body; Effra's transport answers an empty 415, a recorded difference.
- **Malformed input.** Decoding is structure-first (the #49 decision), so a malformed body answers 400 before any transformation or service runs; a transformation's named failure is its mapped response, never 400. Effect wraps payload `SchemaError` as `HttpApiSchemaError` (400 by default) and runs transformations per field.
- **Elixir Plug comparison** (`~/.cache/repo/elixir-plug/plug`). `Plug.Parsers` answers the same statuses through exceptions carrying `plug_status`: 413 `RequestTooLargeError`, 415 `UnsupportedMediaTypeError`, 400 `ParseError` (`lib/plug/parsers.ex:2-38`, raised at `:351` and `:360`; JSON decode errors wrap at `lib/plug/parsers/json.ex:101`). Plug's JSON parser also accepts `+json` subtypes (`parsers/json.ex:73-79`); Effra accepts only `application/json`, a recorded difference. Without a Content-Type Plug skips body parsing entirely (`parsers.ex:319-322`); Effra follows pinned Effect and reads it as JSON. `Plug.Router` has no automatic 405: an unmatched request falls to an explicit `match _` clause (`lib/plug/router.ex:18`), consistent with the 404 profile.
- **MoonBit comparison** (`~/.cache/repo/moonbitlang/core` at `e96ede8`). Core has no HTTP server; its `FromJson` decoding raises one `JsonDecodeError((JsonPath, String))` type for every failure (`json/from_json.mbt:21-28`), so a server built on it cannot separate malformed input from a conversion's domain failure by type. Effra's endpoint mapping depends on exactly that separation.
- **Routing.** Exact static paths and a wrong-method 404, the profile already selected for the transport; duplicate method/path entries in one route table are refused. Go `net/http` `ServeMux` answers 405 for a wrong method, which this profile deliberately does not.

## Unary RPC contract

Define a reusable method table from request/success/failure codecs and typed effect handlers. Keep dispatch, serialization and transport separate. The initial profile uses pinned Effect's whole-message JSON RPC-over-HTTP transport: one Request per POST, a string or numeric request ID preserving its JSON type, and an array containing its terminal Exit response (or the protocol's fatal Defect). The real pinned client emits numeric IDs. It is not a claim of full JSON-RPC standard support.

Capture actual pinned Effect Request, Exit Success and Exit Failure messages as source-controlled vectors. Typed failures, defects and interruption must remain distinct. Match malformed envelopes, unknown tags, invalid payloads, body/admission bounds, cancellation and active shutdown. Batching, streaming, notifications and WebSocket are outside this profile and must be rejected consistently before domain work.

RPC framing is separate from HTTP endpoint validation: malformed JSON or invalid ID produces HTTP 200 with a protocol Defect; an unknown method or invalid payload produces HTTP 200 with an Exit Die. A mapped named transformation failure belongs to the method's declared failure union, not an automatic malformed-input response. Capture actual fatal-defect and interruption frames and configure the same fatal-defect mode in every cohort. Upstream accepts batches; this single-request profile's rejection is a deliberate difference, using one bounded Defect response with no domain work. A valid Request never completes with an empty array or without a terminal response. Engine-specific parse-error text is not a portable contract.

Acceptance requires the real pinned Effect RpcClient against the Effra server and a source/client fixture against the pinned Effect server. HTTP and RPC can reuse the same domain handler and codecs. Handwritten custom `{ok: ...}` framing is not a compatible implementation.

## Delivery graph and gates

1. Shared bundled interfaces, checked type applications and typed function values.
2. Reusable codec modules and canonical derivation.
3. Managed HTTP transport and typed endpoint composition.
4. Unary RPC dispatch/serialization on the same contracts.
5. Public fixtures, canonical tooling agreement and independent framework conformance review.
6. Matched framework measurements and fair profile-guided optimization.

Each logical implementation unit must compile and pass the full repository gate. Run race tests for native runtime changes. Independent review must challenge negative paths and compile scaling, rather than treating broad tests that contain one expected error as proof of every clause. Preserve source/build hashes and raw results. No scored benchmark runs while builds/tests are competing for the host.

The [benchmark contract](server-benchmarks.md) governs workload equivalence, resources, ordering and claims. A readiness flag alone is insufficient: framework admission depends on executable conformance receipts tied to source hashes. Full library parity remains separately tracked; completion here establishes a concrete buffered server slice.

## Prior art: Elixir and MoonBit

Elixir 1.18's `JSON.decode` yields string-keyed maps and `nil` for null, with no decoding into structs, and `@derive {JSON.Encoder, only: [...]}` derives encoding only (`lib/elixir/lib/json.ex:L4-L33`, `L314-L326` at `91ee75bb`). `Plug.Parsers` defaults to an 8 MB body limit and raises 413, 415 or 400 errors (`lib/plug/parsers.ex:L46-L80` at Plug `73404f85`). MoonBit derives `ToJson`/`FromJson`, but its docs call JSON derivation "mainly for debugging" with "unstable" arguments, require an enum `style`, and encode `Option` as `T | undefined` for a direct struct field but `[T] | null` elsewhere (`next/language/derive.md:L121-L199` at docs `8d9f3ba2`). Its `@json.parse` defaults `max_nesting_depth` to 1024 (core `json/parse.mbt:L62-L66`). Effra's codec contract differs on each point: decoding produces nominal data with directional rows, both directions derive together, the wire representation is an explicit policy, and `maxBodyBytes`/`maxDepth` are required with no default. Pins are in [PRIOR_ARTS](../../PRIOR_ARTS.md#elixir-with-erlangotp).
