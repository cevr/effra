# User-defined lint rules

Status: authorized owner requirement, 2026-10-06. Users must be able to write and distribute their own rules without forking the compiler. Reuse the [shared diagnostics and full types](semantic-tooling.md), including exact source revisions and resolved binding identities. This is an implementation contract, not current plugin support.

## API and authority

A rule declares a namespaced identity, version, documentation, default severity, supported target/schema versions, validated options and required fact families. It receives a read-only snapshot and returns findings. The runner owns configuration, severity overrides, reasoned suppression, ordering, limits and projection to public diagnostics. A rule cannot mutate the checker, add proof, turn invalid source into checked source, remove compiler diagnostics or redefine reserved compiler/built-in rule IDs.

Expose source/token spans, typed syntax nodes, resolved declarations/bindings, canonical referenced types, callable failure/service rows, provider origins/dependencies and ownership evidence as supported fact families. A rule must not reconstruct import aliases, lexical shadowing or effect contracts from identifier spelling. Availability is explicit: a syntax-only rule can run on successfully parsed syntax; parser recovery is unavailable in this slice. A rule requiring checked types does not run on unchecked source. Missing facts and unsupported schema versions are reported as unavailable or failed execution, never a clean rule pass. Initial implementation may require checked source for every external rule and explicitly report skipped rules.

Snapshots retain the compiler semantic revision and the shared analysis-producer identity. A separate analysis identity incorporates rule-pack executable/content hashes, versions, configuration and diagnostic policy; changing a lint option must invalidate lint results without pretending the program's type changed. A pack's declared inputs are its protocol request and its qualified process environment (the host variables its configuration selects); it must produce deterministic results from them. Cache only complete results within one process and qualified snapshot; persistent cross-process result caching is outside this slice because undeclared external inputs cannot be validated. Schema/version incompatibility and cyclic or unsupported fact requirements fail explicitly.

## Distribution and execution

The initial extension boundary is a versioned executable rule-pack protocol with a small Go SDK. A pack can be built and tested independently and loaded by the installed ef command, without a compiler rebuild or Go shared-library ABI dependency. The protocol is language-neutral, so a later Effra or JS authoring adapter can use the same facts; neither is required for Go users. Do not advertise an Effra-native rule SDK before the necessary library/IO support exists.

Use a static manifest for metadata and rule selection, plus an explicit executable and argument array. No shell command interpolation, implicit package download or automatic build during lint. One bounded request carries the chosen snapshot/fact projection and validated options; one bounded response identifies the request, snapshot, rule and findings. Use deterministic framing and document protocol limits. The runner validates namespaces, severity, message sizes, source ownership, ranges, related locations, edits and revision before accepting output. An executable cannot claim findings on a different source or masquerade as the compiler.

Each pack is project-supplied executable code, not a sandboxed proof engine. Run only explicitly selected packs (`--rules` or an explicitly supplied lint configuration); discovery/inspection alone does not execute them. MCP and LSP receive the same explicit configuration at server startup/initialization. Existing server sessions without custom rules remain read-only compiler analysis. Do not add a recurring interactive approval flow. Bound wall time/output, propagate cancellation and reap owned processes; a crashed, malformed or timed-out enabled pack makes analysis incomplete and fails its lint policy. Publish built-in findings even when an optional extension fails, with an explicit execution-status field.

Built-in checking and ordinary builds never start external packs. Custom lint cost is measured separately from frontend checking, including cold process startup and requested fact serialization. Run selected rules together rather than starting a process per AST node. Optional pack code is absent from application executables.

## Configuration and surfaces

Supply per-rule off/error/warning/information/hint settings, validated options and named presets. Keep default severity and configured severity distinguishable; strict policy changes failure behavior without changing displayed severity. Unknown rules/options, duplicate identities and reserved namespaces diagnose early. Existing reasoned next-line suppressions can name registered external rules and undergo the same malformed/unknown/unused checks; they never disable mandatory compiler diagnostics.

Distinguish suppression syntax from rule execution. Built-in names are unqualified; external names use `namespace/rule`. Malformed directives and unknown unqualified rules remain errors. A selected namespace with an unknown rule also diagnoses. A qualified namespace absent from the selected packs is not executed merely to validate a directive. Report suppression status as applied, unused, or not-evaluated with a reason: unchecked-source, pack-not-selected, rule-off, pack-failed or facts-unavailable. Only a completed applicable rule can establish that its suppression was unused. Not-evaluated is visible in structured reports and does not itself fail policy. Match external findings by the start line of their primary range. The shared runner implements this for built-in and pack rules alike (see [suppression states](#implemented-stage-three-suppression-states)).

A failed enabled pack publishes a reserved lint-runner Error with its identity, in addition to retained built-in findings and per-rule execution status. The LSP projects it at document range 0:0–0:0 so incomplete analysis cannot look clean. CLI exits 1 for a failed policy, including incomplete pack execution; invocation/configuration/options/admission errors detected before execution exit 2. MCP returns an analysis result with failed policy and `complete: false`. Invalid configuration must not start a pack.

`ef lint`, `ef diagnostics`, MCP equivalents and LSP use the same enabled registry and analysis result. `ef lint rules` and MCP `lint.rules` expose selected pack identities, versions, option metadata, effective severity and fact requirements without running rule code. All reports identify enabled/disabled/skipped/failed rules sufficiently to distinguish no findings from incomplete analysis.

Findings may propose revision-bound text-edit suggestions. The first slice exposes validated previews only: diagnostic queries never rewrite source. Reject out-of-range, overlapping or cross-snapshot edits. Applying edits or advertising LSP code actions requires a separate checked-edit contract with stale-source guards; a proposed fix is not a proof of semantic preservation.

## Authoring and acceptance

Ship a small external Go rule-pack example and a source-fixture test runner. Fixtures contain real `.ef` programs and expected codes/severities/ranges, with admitted controls, rather than mocked AST objects that can hide resolution bugs. The pack receives the production snapshot through the same protocol used in CLI/MCP/LSP. Tests can assert suppression and suggested edits without mutating fixtures.

Demonstrate two unrelated rules using the same extension seam:

1. A project policy restricting a configured live provider to declared composition functions. Use resolved provider identity and provision edges; same-spelled local values must not match.
2. A project policy forbidding a configured failure in selected function identities. Inspect canonical nominal failure identity and complete rows, including helper forwarding. Same-spelled locals, record fields, string literals and comments must not match. Cover an error removed by recovery and errors contributed by timeout/interop operators through their declared rows. The current language has no visibility modifier or failure aliases; alias acceptance follows the future module/alias feature rather than a vacuous fixture.

Neither policy becomes a universal language restriction. User configuration names the permitted boundaries and severity. Compare admitted provider aliases, shadowing, negative cases and allowed exceptions; no name-only pseudo-type checker. Require real checked source for checked-fact rules. Cover applied, unused and every not-evaluated suppression state through the same public protocol.

Deliver three gated units: versioned fact/registry/SDK seam; bounded executable runner plus source-fixture tests; CLI/MCP/LSP configuration/reporting, examples and docs. Cover malformed/oversized output, hanging/crashing process, unavailable facts, stale snapshot, invalid options/ranges, independent pack failures, duplicate IDs, suppression, precise Unicode positions and cross-surface parity. Preserve compiler errors even if a malicious test pack requests their removal. Retain raw cost receipts for disabled and enabled rules, with no unmeasured compilation-speed claim. Full gate and independent review precede closure.

### Implemented stage one: facts, registry and Go SDK

The public package `effra.local/prototype/lint` imports no compiler package. Fact schema `effra.lint.facts` version 1 has independently available families: `declarations` (services, providers, failures), `callables` (source functions, service operations and provider methods with declared and checked body rows plus row contributions), `calls`, `provisions` (direct and per selected layer node, with the resolved provider identity), `bindings` (checked lexical bindings and resolved uses) and `imports`. Rows hold nominal identities: source failures use their declaration identity and compiler failures `error:builtin:<name>`. `Result.LintFacts` derives requested families from retained checker resolutions. Unchecked source makes every family unavailable as `unchecked-source`; exhausted lexical facts make `bindings` unavailable as `fact-budget-exhausted`. Snapshots carry the semantic schema, revision, target and producer qualification, are deterministically ordered and contain no source spelling beyond declaration display names.

A pack manifest (`manifestVersion` 1) declares namespace, version, accepted fact versions, an explicit executable path and argument array, and per-rule version, documentation, default severity, required families, targets and an option schema (`string`, `boolean`, `integer`, `string-list`, enum, required/default). Manifests, configuration (`version` 1, rule keys `name` or `namespace/name`, severity `off|error|warning|information|hint`, options) and options decode strictly: unknown fields, duplicate keys and trailing data are refused, as are null option values, null string-list elements (including manifest defaults) and an explicit null or empty severity; an omitted severity selects the default. The registry combines unqualified built-in rules with selected manifests and refuses reserved or duplicate namespaces and duplicate rule IDs; configuration refuses unknown namespaces and rules, invalid severities, a configured severity for `invalid-suppression`, and invalid options. Pack identity digests the manifest; configuration identity digests effective severities and options, whether a target-limited rule is enforced (see target applicability), and each pack's selected environment variable names; the analysis identity combines them with the fact schema, the qualified semantic snapshot and the digest of the snapshot's wire form (the document URI, byte count and every fact family a pack receives), and is not reusable for an unqualified snapshot. Equal source content under two document URIs is two analyses. A pack's report also commits to the digest of the request that pack was sent, without its `id`: the namespace, version and manifest identity it names, its admitted rules with their effective options, and the snapshot. Two selected packs that share one executable are therefore two analyses. Building, configuring and inspecting a registry reads metadata only.

`lint.Apply` is the single in-process rule execution path. It recovers a panic as failure and refuses empty or oversized messages and spans outside the source admitted before the rule ran; a rule that enlarges its own snapshot's source bound cannot authorize output. Output-count limits belong to the custom-rule runner (1,000 findings per rule), not to `Apply`: built-in rules report every finding to suppression and lint policy, as before the migration. `lint.Evaluate` runs a Go pack in-process, giving each rule a private copy decoded from the snapshot's wire form: it reports per-rule `completed`, `off`, `skipped` (unavailable family or target) or `failed` (incompatible fact schema, error, panic, invalid output) and `complete: false` unless every enabled rule completed. `redundant-provision` and `unused-go-import` run through `Apply` over facts with unchanged diagnostics; `unused-recipe` keeps its scoped walk because its binding facts can be unavailable. `examples/lintpack` implements both policy examples over real fixtures.

### Implemented stage two: bounded process runner

`lint.Run` executes one selected pack as a separate process over protocol version 1, and `lint.Evaluate` is the same path without the process: both admit rules identically, send the same `Request`, run rules through the same SDK handler and validate the `Response` with the same code, including its serialized size against the response byte limit (`Evaluate` applies the default limits). Off, skipped and admission-failed rules are decided without starting the pack, and no process starts when no rule may run. A frame is the ASCII header `EFFRA-LINT <version> <length>\n` (canonical decimals, at most 64 bytes) followed by exactly `length` bytes of JSON. The pack reads one request frame from stdin until end of input, writes one response frame to stdout and exits 0; stderr is diagnostics. The request carries the pack identity, each admitted rule's manifest version and effective options, the snapshot in its fact wire form, and an `id`: an opaque commitment to all of these and to the execution answering them (see the environment policy below). The response must echo the `id` and the snapshot revision and return exactly one `completed` or `failed` result per requested rule; the whole set is checked before any result is recorded, so a refused response publishes no finding and exactly one failed status per requested rule. A Go pack's `main` is `lint.Main(pack)`. A pack that does not speak the request's version answers with a frame of its own version.

The executable path is never looked up on `PATH` or interpreted by a shell. A relative path resolves against the caller's directory (the manifest's directory), independently of any PATH the pack receives. On Windows, starting a path without a `PATHEXT` extension starts the first existing `path.com`, `path.exe`, …; the runner resolves that file once (`exec.LookPath` on the absolute path, which never searches PATH), then hashes and starts exactly it. A pack executable that resolves to a `.bat` or `.cmd` file is refused, at selection as an invalid invocation (exit 2) and at run time as `spawn-failed`: cmd.exe runs batch files with its own command-line parser, which breaks the argument contract. A Windows-only test covers this resolution and refusal over real files through the production lookup; it has not yet run on a Windows host. The process environment is exactly `RunOptions.Env` (empty when nil), except for Windows `SYSTEMROOT` (see the environment policy below). The pack runs as the leader of a new process group. Limits default to 30 s wall time, a 16 MiB response, 10,000 findings per response (1,000 per rule) and 16 KiB of retained stderr (the rest is drained). On Linux, a 2 GiB data-segment limit (`RLIMIT_DATA`) is applied before the request is written. A timeout, cancellation or framing violation kills the whole process group. After every exit, the runner kills the group again, so no descendant that stayed in the group outlives the pack, and the runner always reaps the pack. A descendant that leaves the group cannot be killed by the runner; if it holds the pack's output open, or holds its input unread while the request is still being written, the write and the reads end after a two-second grace period and the run fails as malformed. These deadlines need pollable pipes, which Go's `os.Pipe` does not provide on Windows, where the runner also has no process group: there, an escaped descendant can still hold a run.

A pack failure is a structured `Report.Failure` (`spawn-failed`, `timeout`, `cancelled`, `crashed`, `malformed-response`, `oversized-response`, `protocol-mismatch`, `stale-response`, `invalid-response`) with the exit status and retained stderr. It is never a host error. Every requested rule is then `failed` with reason `pack-failed: <code>`, no finding of the pack is reported, and the analysis is incomplete. The runner validates every response against the source bound and revision it copied at admission, never against state a pack or rule can write. A response for another revision is stale. A response for another request, or one that names an unrequested rule (including built-in or compiler names), repeats or omits a rule, or uses another status, is invalid. Unknown fields such as a field trying to suppress compiler diagnostics are malformed. The response cannot express severity, rule identity or removal of other diagnostics. An invalid result of one rule fails only that rule; its findings are never partially accepted. Findings may carry `suggestions`: edits must lie inside the snapshot's source, must not overlap or share a start offset, and are bounded in count and text size. They are previews bound to the report's semantic revision and are never applied.

`examples/lintpack/cmd/policy-lint` serves the example pack. Over the protocol, on the real fixtures, it reports exactly what in-process evaluation reports. Tests start real processes for crash, nonzero exit after a response, hang (timeout and cancellation, with pack and same-group descendant reaped), a descendant left by a successful pack, a descendant escaping the group with the pack's output or with its unread input, malformed and trailing output, oversized header and finding counts, protocol version mismatch, stale and foreign responses, masquerading rule names, edit validation and the memory limit.

### Implemented stage three: configuration and pack selection

A lint configuration document (`version` 1) may select packs, extend presets and set rules: `{"version":1,"packs":[{"manifest":"lint/policy.json"}],"extends":["policy/strict"],"rules":{...}}`. `lint.LoadConfig` reads it and every selected manifest as bounded regular files. A relative manifest path resolves against the configuration file's directory, never the caller's working directory, and the manifest's own directory then resolves its executable and is the pack's working directory. Any unreadable, oversized or invalid file refuses the whole configuration. Every file is admitted as the CLI and MCP admit source files: a path that names a FIFO, device or directory is refused before it is opened, so loading never waits for a writer. A selected manifest's executable, if it exists, must be a regular file too, which loading checks without opening it; an absent executable loads, so rules can be inspected before a pack is built. When no Windows program file resolves, loading checks the declared path itself, since the Windows lookup reports a directory there as not found: only a path where nothing exists is absent. The runner admits the executable again before each run, where a missing or special file is a `spawn-failed` pack failure that never blocks. A pack declares named presets in its manifest (`presets: [{name, description, rules}]`, keyed by its own rule names). Manifest validation checks a preset like configuration of that pack, so a preset cannot configure built-in rules or another pack. `extends` names presets of selected packs as `namespace/preset` and applies them in order, and the document's `rules` apply last. Each layer overlays what it states: a stated severity or options replaces the earlier value, and an omitted one keeps it. An unknown or repeated preset, or one of an unselected pack, is a configuration problem. A preset has the configuration identity of the settings it expands to.

A report from a pack process carries an execution identity: the absolute program path the runner started (the process's first argument), its working directory, a length-framed digest of the exact bytes of both (JSON text replaces bytes that are not UTF-8, which a Unix path may hold), and the SHA-256 of the executable file the runner read just before starting it. The analysis digest includes it, so equal output from different program bytes, or from the same bytes started from another path or directory, is a different analysis. When that content cannot stand for the pack's implementation, the execution identity is incomplete and the report's reuse scope is `none`: this covers a script starting with `#!` (its interpreter runs code outside the file) and manifest arguments (which can name further code). The libraries a native executable loads are outside the identity either way. A pack that does not start (every rule off or skipped) has no execution identity. `lint.Evaluate` runs in-process and has none either. Its findings and statuses equal the process path's. Its analysis identity is marked `inProcess` with reuse scope `none`, and its request ID is bound in a separate in-process domain: in-process evaluation cannot apply a per-pack OS environment and never claims process qualification.

### Implemented stage three: surfaces

`ef lint`, `ef diagnostics`, `ef lint rules`, `ef mcp` and `ef lsp` accept `--lint-config FILE` (at most once) and `--rules MANIFEST` (repeatable; joins the configuration's own packs). An empty path is refused, never read as no selection, and an empty `--lint-config` still counts as its one occurrence. They load the configuration once, at startup, through `internal/lintpacks`. Every surface then runs the same session: CLI per invocation, MCP per `project.lint`/`project.diagnostics` call, LSP per synchronized document. A configuration that does not load, a duplicate namespace or an invalid rule setting is an invalid invocation (exit 2), and no pack starts. `ef lint` now uses exit 2 for every invocation error, as `ef diagnostics` does, including a source path without the `.ef` extension. Exit 1 remains failed policy, which includes incomplete pack execution. `ef lint rules` and MCP `lint.rules` return the configuration's rule inspection (`rule`, `builtin`/`pack`, pack identity and version, default and effective severity, requirements, targets and options) without running a pack. Without a selection, they list the four built-in rules at their default severities.

Over checked source only, the selected packs run in parallel over one shared fact snapshot. That snapshot carries the families every enabled pack rule requires, and the document URI. Reports come back in namespace order, whatever the selection or completion order. `Result.LintWith` and `DiagnosticReportWith` merge them with built-in advice:
- A pack finding becomes a lint diagnostic whose code and rule are the qualified `namespace/rule`. It keeps its related locations and suggestions, and the LSP projection carries the related locations as `relatedInformation`.
- A failed pack, or a pack rule that failed, becomes one `EFL000` `lint-runner` error naming the pack and its manifest identity. Built-in findings and other packs' findings remain.
- A skipped pack rule is a lint-runner error too, with its reason (`facts-unavailable` or `target-unsupported`): incomplete pack execution fails policy (exit 1), and MCP and LSP report it with `complete: false`. An enabled rule that did not run has not passed. The one exception is target applicability, below.
- A rule that declares `targets` is skipped under any other target, with reason `target-unsupported: <target>`. Who enabled it decides what that skip means. Enabled only by its pack's default severity or by a preset, the rule does not apply to that target: its status is `skipped` with `inapplicable: true`, it reports no finding, `complete` stays true and policy is unaffected. Enabled by the project's own configuration (a `rules` entry at any severity but `off`, with or without options), it is enforced: the project asked for a guarantee this target cannot give, so the skip is an `EFL000` lint-runner error and policy fails (exit 1). One MCP server therefore lints both targets under one configuration. The setting's `enforced` flag is part of the configuration identity and is shown by `ef lint rules` and `lint.rules`. Every other skip and every failure (missing facts, a crash, a timeout, a protocol error) still fails policy. This follows Gleam, which filters target-specific definitions silently but errors when the root package itself requires one its target lacks, and ESLint's per-language rule metadata.
- Lint results carry `complete` and a per-pack `packs` status (analysis identity, failure, rule statuses). Diagnostic reports carry `lintComplete`.
- An `EFL000` without a source location has `locationAvailable: false` and an LSP range of 0:0–0:0, so the LSP publishes it rather than dropping the document's diagnostics.
- Lint findings order by byte offset. On equal offsets, built-in advice comes first and then packs in namespace order. The diagnostic report keeps its total order.
- Built-in rules follow the configuration. `off` removes a rule, and a suppression naming an off rule is not reported unused, because the rule did not run. A configured severity replaces the default, and `hint` displays as the built-in vocabulary's `suggestion`.

A finding position is a UTF-8 byte span with the compiler's 1-based line and 1-based byte column. The surfaces hand the runner the analysed text (`Source.Text`, never sent to a pack). Before it accepts a finding, related location or suggested edit, the runner checks three things: that the span starts and ends on character boundaries, that its line and column are the ones its offset has, and that the text has exactly the snapshot's byte count. A pack that misplaces a finding fails that rule, which reaches every surface as a lint-runner error. A pack cannot publish a position that the CLI prints in one place and the LSP shows in another. An accepted pack finding is then projected exactly as a built-in finding is, so its UTF-16 LSP range matches the compiler's for the same bytes. Without text (a host that supplies none, or the pack side of the protocol), only the byte bound is checked.

`ef lint test PATH... [--update] [--target go|js] (--lint-config FILE | --rules MANIFEST...)` is the pack author's fixture runner. Each `.ef` file (or each `.ef` file in a directory, sorted, not recursive) is a real program. It compiles and runs through the same session, process protocol and merge as `ef lint`, so a fixture tests the built pack exactly as users run it. `name.ef` expects `name.lint.json`: `complete`, every pack rule status and the pack findings with code, severity, message, byte span, line/column, related locations and suggested edits, plus any lint-runner errors. Built-in advice is outside an expectation, so compiler rule changes do not churn pack fixtures. A fixture with no findings is a negative control. Expectations compare by content, and a mismatch prints both. `--update` rewrites expectations atomically and never modifies a fixture. A fixture that does not check, a missing or invalid expectation (including any data after its one JSON object), or a mismatch fails the run (exit 1). No fixture, no selected pack (including a configuration that selects none) or an invalid configuration is an invalid invocation (exit 2), and so is a fixture or an existing expectation that is not a regular file; expectations are admitted before any pack runs, without opening a special file. Pack-side unit tests can still call `lint.Apply`/`lint.Evaluate` in process. Only the command exercises real compiled facts, because the compiler packages are internal to Effra.

### Implemented stage three: process environment policy

A pack process receives an explicit allowlist of host variables, empty by default (decision `lint-pack-environment`, 2026-10-07). A configuration's pack entry names them: `{"manifest":"lint/node.json","env":["PATH"]}`. A manifest preset may state `env` too. Selections merge like rule settings, in this order: extended presets, then the pack entry. An omitted `env` keeps the earlier selection, and a stated array replaces it (`[]` clears it). Names match `[A-Za-z_][A-Za-z0-9_]*`, compared exactly on Unix and without case on Windows. Values, wildcards, interpolation and inheritance modes do not exist. An explicit `null` or a non-string name refuses the document. An invalid or repeated name is an `invalid-environment` problem that names the pack and the name, never a value. Like every configuration error, it exits 2 before any pack starts. `ef lint rules` and MCP `lint.rules` show each pack rule's selected names.

Each analysis captures the Effra process's own environment once, before its packs run in parallel. Every pack's selection resolves from that one capture: a missing variable stays absent, a present empty one stays present and empty, and nothing else passes. No PATH, HOME, TMPDIR, locale or NODE_OPTIONS default is synthesized. A long-lived MCP or LSP server recaptures its environment for every analysis, so a change outside the server needs a restart to be seen. The allowlist is the selection plus the platform's required variables (`lint.RequiredVariables`): on Windows that is the host's `SYSTEMROOT`, which a process needs to start, and elsewhere nothing. That `SYSTEMROOT` must be nonempty: otherwise the pack fails as `spawn-failed` without starting, which is a lint-runner error and exit 1. Every Windows entry must also be UTF-8. These Windows paths are verified by unit tests and cross-compilation only; no Windows process has run.

The runner admits the environment once, so a later entry for a name replaces an earlier one, and the process receives exactly what the identity names. The execution identity adds a digest of that environment: the policy version, the GOOS/GOARCH platform, and each variable's canonical name and value bytes, length-framed. An empty value therefore differs from an absent one, and no encoding can merge two values. It also lists the variable names, never their values. Selection order and unselected host variables do not change it, while a selected value or presence change produces a different analysis without changing the configuration identity or the semantic revision. The request `id` digests a domain-separated envelope of the request and this execution identity, so a response computed under another executable or environment cannot bind. Packs keep echoing the `id` as an opaque value, and protocol version 1 is unchanged on the wire. Hashing is an equality mechanism, not confidentiality. A pack can still echo a selected value in its own findings or stderr, so prefer rule options for policy settings and keep `env` for runtime needs. Hashing PATH or HOME does not fingerprint the files they lead to, so selecting variables grants no persistent or cross-process cacheability.

### Implemented stage three: suppression states

A next-line directive `// effra-lint-disable-next-line RULE -- REASON` keeps the reasoned grammar and the single `EFL004 invalid-suppression` code of the built-in suppressions. `RULE` is an unqualified built-in name or `namespace/rule`. `lint.Configuration.SuppressionTarget` classifies it from metadata alone, so no pack starts to validate a directive:
- A known built-in rule, or a rule of a selected pack, is suppressible. The fixed `invalid-suppression` rule is not.
- A qualified name whose namespace or rule is not an identifier (`Acme/rule`, `acme/a/b`, `acme/`) is malformed (`EFL004`).
- An unknown unqualified name, an unknown rule of a selected pack and a reserved namespace (`effra/…`, `builtin/…`) are unknown (`EFL004`). Directives therefore cannot name compiler codes (`EF108`) or the lint runner (`lint-runner`).
- A well-formed name in a namespace that no selected pack has is admitted without diagnosis.

Every admitted directive gets one `SuppressionStatus` (`rule`, `status`, `reason`, the directive `span`, and the 1-based covered `line`), in source order. The runner decides each status once every rule that could run has run:
- `applied`: the directive removed at least one finding of its rule whose primary range starts on the covered line. The rule can be built-in or a pack rule. Suppressed findings are removed before counting and policy.
- `unused`: the rule completed with no such finding. This is also an `EFL004` error, as before.
- `not-evaluated` with a reason:
  - `unchecked-source`: no rule runs. This applies to built-in directives too: unchecked source no longer reports them unused.
  - `pack-not-selected`
  - `rule-off`: the rule is configured off. This applies to built-in rules too; they used to be silently dropped.
  - `pack-failed`: the pack failed, its rule failed, or the pack has no report.
  - `facts-unavailable`: a required family is unavailable. For a built-in rule, the rule did not complete.
  - `target-unsupported`: covers inapplicable and enforced target skips alike.

`target-unsupported` is a sixth reason because target applicability postdates the five-reason list. Folding it into `facts-unavailable` would misreport why the rule did not run. A not-evaluated status adds no diagnostic and does not change policy. Policy still fails through whatever made the rule not run: an `EFL000` for a failed or enforced pack rule, or the compiler errors of unchecked source. A suppression never removes a compiler diagnostic or an `EFL000`, which have no rule a directive can name.

`LintResult.suppressions` (`ef lint`, MCP `project.lint`) and `DiagnosticReport.suppressions` (`ef diagnostics --json`, MCP `project.diagnostics`) carry the statuses. The diagnostic report adds each directive's zero-based UTF-16 `range`. It carries statuses for unchecked source too, while its lint findings stay omitted there. The LSP cannot put them in `publishDiagnostics`. A client that declares the experimental client capability `effraLintStatus: true` receives an `effra/lintStatus` notification after each publication: the document `uri`, `version`, `revision`, `lintAvailable`, `lintComplete` and the report's `suppressions`. One diagnostic report feeds all three surfaces, so their statuses and ranges are identical. `ef lint test` expectations record the statuses of `namespace/rule` directives as `suppressions`; the field is omitted when there are none, so existing expectations keep their bytes. Tests cover every state and reason through CLI, MCP and LSP over real pack processes (`internal/lintpacks/suppression_test.go`). `facts-unavailable` uses a 250 KB source past the lexical fact budget, inside the LSP document limit. Compiler-level tests cover malformed, unknown and compiler-error cases (`internal/compiler/lint_suppression_test.go`), and the fixture command is tested in `cmd/ef/lint_packs_process_test.go`.

Rejected alternatives:
- Report a directive unused when its rule is off. ESLint does this: an off rule is resolved, never runs and its directive is reported unused (`lib/linter/apply-disable-directives.js:371-376`, `548-551` at `a39d9fb`). Biome's analyzer reports any suppression that suppressed no signal (`crates/biome_analyze/src/lib.rs:268-317` at `a3944f7`). Silence from a rule that did not run proves nothing, and toggling a rule would churn every directive. We follow golangci-lint, which drops unused candidates for linters that are not enabled (`pkg/result/processors/nolint_filter.go:110-116` at `8ea3d53`).
- Diagnose a directive for an unselected pack. ESLint reports "Definition for rule … was not found" (`lib/linter/linter.js:283-285`). Packs are explicit selections that legitimately differ between an editor and CI, and starting a pack to validate a directive is forbidden. golangci-lint likewise only logs unknown linter names (`nolint_filter.go:97-105`). Effra keeps unknown names in a selected namespace or a reserved namespace as errors, as Biome's `suppressions/unknownRule` does (`crates/biome_analyze/src/suppressions.rs:564-605`).
- Make the reason optional. ESLint's `-- description` is optional. Biome requires a reason (`crates/biome_suppression/src/lib.rs:415-420`), and golangci-lint's nolintlint can (`require-explanation`). Effra keeps it mandatory, per justify-don't-ban.
- Report not-evaluated as a hint diagnostic. Every editor without the CI-only pack would then show noise on correct directives, and no inspected linter does it. A parallel `publishDiagnostics` extension field was also rejected: unknown fields have no defined client behavior. Opt-in custom server notifications have precedent in rust-analyzer's `experimental/serverStatus` and clangd's `textDocument/clangd.fileStatus`.
- Credo's model (Elixir; `rrrene/credo` at `90c5541`). `# credo:disable-for-next-line`, `-this-file`, `-previous-line` and `-lines:N` (`lib/credo/check/config_comment.ex:7-52`) name one check module or a regex, and they have no reason field. The rest of the line becomes the check atom (`config_comment.ex:139-142`), so a misspelled or unloaded check silently suppresses nothing. The opt-in `Credo.Check.Design.RedundantConfigComments` reports any comment that ignored no issue, including one whose check the configuration disabled (`lib/credo/check/design/redundant_config_comments.ex:8-12`, `39-63`). Effra rejects four parts of this: regex targets (a directive must name one rule), the missing reason, unvalidated names, and treating a config-disabled rule as unused. Elixir's compiler has no per-site warning suppression comment. It silences undefined-function warnings per module with `@compile {:no_warn_undefined, …}` (`elixir-lang/elixir` at `91ee75b`, `lib/elixir/lib/module.ex:606-607`), and `--warnings-as-errors` changes policy, not visibility. That matches Effra's split between configuration (severity, `off`) and reasoned per-line acknowledgement.
- MoonBit's model (`moonbit-docs` at `8d9f3ba`). Warnings are configured per package with `warnings = "-unused_value"` / `"warn-list"` and per module, plus `--warn-list`, `--alert-list` and `--deny-warn` on `moon check` (`next/toolchain/moon/package.md:1043-1106`, `next/toolchain/moon/commands.md:111-114`, `154-155`). The only per-site control is a `#warnings("-name")` attribute on a top-level declaration. It takes no reason and "only works with some specific warnings" (`next/language/attributes/warnings.md:3-26`). Effra keeps declaration-wide or package-wide silencing in configuration, where it is visible in the configuration identity. In source it admits only a next-line acknowledgement with a reason, because a declaration-scoped switch hides later findings in the same declaration without review.
- A second directive grammar such as `effra-ignore`. It would duplicate formatter attachment rules and `EFL004` validation. The owner's effect-oxlint plugin (`ca2ce6a`) instead holds plugin rules to the host's one directive. Its rules are namespaced (`effect/noUnboundedRetry`) inside oxlint's `oxlint-disable-next-line`. Its `effect/requireSuppressionReason` requires every directive to name its target and give a `--` reason, and it rejects a wrongly qualified name rather than ignoring it (`README.md:83-90`; `tests/syntax-platform-rule-edges.test.ts:526-533`).

### Implemented stage three: cost receipts and the build/run control

`ef lint receipt FILE [--runs N] [--target go|js] (--lint-config FILE | --rules MANIFEST...)` prints a raw cost receipt (`kind: effra.lint.cost-receipt`, `version: 1`). It runs the same `internal/lintpacks` session, runner and merge as `ef lint`, but on a separate path (`Session.Receipt`), so `ef lint` itself measures nothing. The header holds:
- the host's GOOS, GOARCH, CPU count and Go version, and the producer identity;
- the source's URI, byte count and target;
- the configuration identity and its rule inspection;
- a `claim` stating that the numbers are raw wall-clock measurements with no aggregate, baseline or performance claim.

Each of the 1–100 runs reads and compiles the source afresh and starts every enabled pack as a new process. Run 0 is the first in its `ef` process, so it includes cold operating-system caches for that process. A run records nanoseconds for:
- `frontendNanos`: read, compile and check;
- `factsNanos`: extracting the families the enabled pack rules require, once for all packs;
- `packsNanos`: all packs running in parallel;
- `lintNanos`: built-in rules, suppressions and merge.

Each pack also gets a `packRun`, filled from `lint.RunOptions.Trace`, an optional hook that never changes a report:
- `prepareNanos` and `snapshotBytes`: fact serialization into the snapshot wire form, plus rule admission;
- `qualifyNanos`: executable hashing and environment admission;
- `encodeNanos` and `requestBytes`;
- `spawnNanos`: process creation;
- `firstByteNanos`: from process creation to the first response byte;
- `exitNanos`: until the process is reaped;
- `responseBytes` and `acceptNanos`: response validation;
- `started`, the rule statuses and any failure.

A pack's own startup cannot be separated from its decoding and rule work without pack cooperation, so `firstByteNanos` bounds both rather than claiming a split. With every rule of a pack off, `started` is false and every process phase is zero. The session derives exactly the families that enabled pack rules require (`Result.LintFactsFor`), so a selection whose pack rules are all off derives none. Its family-free snapshot is still serialized for the analysis identity, and the receipt shows that cost. Before receipts existed, an empty requirement fell through to `LintFacts()`, which means every family. The first disabled receipt exposed this, and a process test now guards it. Receipts are evidence for the benchmark phase, not a measurement claim; none is checked in. A process test covers both the enabled and the disabled receipt (`cmd/ef/lint_cost_process_test.go`).

`ef build` and `ef run` refuse `--lint-config` and `--rules`, and no other path selects a pack, so they never start one. Emitted programs link no lint SDK or pack code. `TestBuildAndRunNeverStartRulePacksProcess` checks this with a pack that records every start in a marker file:
- both lint flags are refused by `ef build` and `ef run`, under both targets;
- building (Go and JS) and running a source whose directive names the pack leave the marker absent;
- neither the native executable nor the JS module contains the SDK's import path, the pack's namespace, its program text or the directive text;
- `ef lint` with the same configuration does start the pack (the positive control for the marker);
- the `ef` binary itself does contain the SDK path (the positive control for the byte scan).

## Prior-art decisions

Go's [analysis API](https://pkg.go.dev/golang.org/x/tools/go/analysis) separates analyzers, typed per-package facts and the driver; adopt explicit metadata/fact requirements and reusable reporting. Its supplied documentation leaves severity to drivers; Effra similarly centralizes configured severity while exposing defaults.

[Oxlint plugin authoring](https://oxc.rs/docs/guide/usage/linter/writing-js-plugins.html) supplies configurable rule metadata, reports and a testing interface. Borrow the authoring/test ergonomics, not a requirement to run JavaScript or duplicate type analysis.

Inspected Effect tooling source: `Effect-TS/tsgo` at `d211e109b14045164934c071120b92947a98c8a1`, `internal/rule/{rule,metadata,context}.go`; rule output is separate from checker attachment, with shared directive/severity emission. The owner's lint-plugin source was refreshed to `ca2ce6aeb7b148293b5662b7fb0613c52e81047c`; its rule builder, testing adapter and alias/suppression/test-isolation policies motivate resolved facts and real-source tests. These are source comparisons, not a claim that upstream exposes this exact external protocol.
