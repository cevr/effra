# Regular language abstractions for the bundled library

Status: authorized extension of the Wayfinder implementation goal, 2026-10-06. The owner asks for Go-like simplicity, Effect-style guarantees and Borgo-like ADTs/abstractions. Upstream source review and independent counsel identify concrete missing mechanisms; exact new syntax remains subject to executable examples and review.

## Design decisions

Keep `run` as the visible execution of a lazy effect recipe. A fiber is already running; a recipe is reusable program data. Preserve ordinary control flow and explicit public function success/failure/service contracts. Local function inference may remove redundant spelling, but it cannot silently widen a public row. Owner-directed [layer inference](layers.md) is a separate explicit rule: optional annotations bound inferred construction contracts.

Use one canonical type representation for nominal identity, applications, function parameters/results and effect rows. String display forms are derived output, not a second semantic authority. Share repeated type structure and keep provenance/evaluation analyses bounded independently; interning types alone does not bound an analysis that enumerates paths through them.

Separate the value produced by an expression from the failures/services incurred while evaluating it. A named effect-function value, a constructed recipe and an executed result are different contracts. Compute evaluation contributions once per checked node rather than repeatedly walking nested subtrees.

Carried callable, recipe and fiber rows belong to their canonical type identities; expression evaluation rows are separate facts. A branch join or record projection cannot replace a carried contract with its own evaluation row. Final checked facts must not accidentally retain an incomplete summary prepass. Named function values also contribute resolved declaration dependencies, including when passed as arguments; respect lexical shadowing when ordering summaries and selecting emission roots.

A typed recipe `Effect<T, {E}, {S}>` is first-class data: a field, payload, application slot, callable result or if/match branch value. Branches join their carried rows and provenance; a branch whose recipe value is discarded remains EF105. Trailing empty rows are omitted from source and display. Its identity is the success type plus the two rows, independent of the producing callable. Outside an application, success is covariant and rows are upper bounds; application slots stay invariant. Storing or passing a recipe never runs it, a discarded recipe statement remains EF105, and each `run` executes it again. Managed handles the recipe already references are held by its container at the field path; what executing it returns stays deferred until that recipe runs. A recipe read from a data field keeps the evidence of its constructing occurrence. A recipe read from a parameter, or one whose occurrence is unknown, holds what its parameter or container holds there, and each layer returns only handles it holds or that one of its executed layers acquired; only a recipe whose held handles are unknown has unresolved result ownership, which is refused at its first use or escape.

`scope { body }` executes its body under a fresh owning scope. Its non-recipe result becomes visible to the caller only after owned child shutdown and resource cleanup complete. Failures, defects, interruption and accompanying cleanup causes retain the ordinary scope contract. A forked child's typed failure is charged to the row of the owner that closes it and to an observing join or interrupt; recovering the forking function does not discharge it unless the child was observed. `fork` itself charges only the child's requirements. A child is observed on a path when a `run` of its `join` or `interrupt` precedes every exit the path may take; `cancel`, a join under `.timeout` and a join inside another child observe nothing. The children a body leaves unobserved stay pending on its call layer, and the next owner edge (scope, timeout, fork child, `.provide(Layer)` or the root) raises them. A callable type, a service method, a parameter, a failure payload and a joined result carry only a type, so a function or recipe that may leave a child unobserved is refused (EF107) where it would reach a consumer through one of them; binding, branching on, running or returning it keeps its evidence. An owner edge raises an ordinary failure only when exactly one failure reaches it, because `recover` and `catch` handle only a solitary typed failure and the runtime raises the body's failure and every unobserved child's cause as one sequence. A completed join or interrupt observes the child; cancel does not, and a join abandoned by timeout does not. On a non-aborted close, pending failures are charged to the closing owner's row. On a cancellation-aborted close (a body ended by interruption, or cancellation requested on the owner's fiber), pending ordinary typed child failures are abandoned under the runtime contract; they do not compose with interruption or a winning deadline, so a `timeout` and the interrupt of a running fiber add no composite. A timed computation's own failure may still be returned when the work wins. Non-aborted composites retain the existing admission rules: a child failure pending together with a failure of the body (an exit taken while the child was unobserved), and the failures of two children (also with equal labels, also through calls), are a composite cause no row can declare, and the function whose owner would raise it is refused (EF107, `composite cause`), while the root permits composites whose typed components `main` declares. A failure handled by `recover` or `catch` before the owner closes no longer reaches it with the child; a join before the exit observes the child.

A final expression whose value is a recipe is not implicitly executed and is not admitted as a top-level scope result. It reports EF105 with a scope-specific explanation and a suggested `run` edit. The rejected scope has the already-reported invalid type, which every dependent later check accepts silently (as Gleam types a rejected expression), so one rejected tail yields one diagnostic while independent errors still report. Binding an unused recipe does not execute it.

`run expression` executes exactly one recipe layer under the current scope, contributes that execution’s failure and service rows, and yields its success value. If that success value is another recipe, it remains a recipe; executing it requires another explicit `run`. The scope-tail rule still applies.

Ownership evidence is indexed by layer. A recipe `Effect^n<T>` records, for each of its n layers, the handles executing that layer holds, and for its innermost value the owners of each managed handle. An owner is a parameter of the enclosing function, a lexical scope, a closed timeout, child or provision owner, or the executor of one of the recipe's own layers, which is unknown until something executes it. Executing a layer binds its executor: `run` to the current scope, `fork` to the child, `.timeout` to the timeout and `.provide(Layer)` to the provision, in each case before that boundary closes. A handle a layer acquires is therefore owned by whichever construct later executes that layer, never by the scope that built the recipe, and an outer layer's acquisitions held by an inner layer keep the outer layer's owner. A function's summary abstracts its body's own scope to the executor of its call layer, so the same rule crosses calls, callable parameters and recovery handlers. Owner sets are exact: a branch join keeps every owner of both alternatives.

No returned value or transitive capture may retain a managed resource owned by the closing scope. Proven outer-owner borrows remain valid; unresolved managed ownership is handled conservatively. Executing a recipe layer (`run`, `fork`, `.timeout`, `.provide(Layer)`) uses the handles that layer holds, so every handle held at layer 0 needs an owner that is provably open there; handles held by later layers are checked when those layers execute. A timeout or forked child owns what its execution acquires only until that execution completes: a recipe produced under it that holds those handles (through recovery, a factory, a branch join or `join`, which re-exports the child's result and held handles to the joiner) is refused when it is later executed, while outer-owner borrows it holds stay usable. Safe inert recipes carried in checked data are not implicitly executed or blanket-rejected. Recipe-result function slots and branch value selection retain their existing rules.

Selecting a recipe and executing it are distinct. In `fn choose(flag: bool) -> Effect<string> { if flag { left() } else { right() } }` the branch selects a recipe value and runs neither. Inside a scope, `scope { run if flag { left() } else { right() } }` and `scope { if flag { run left() } else { run right() } }` both run only the selected recipe, once, before the scope closes; `scope { if flag { left() } else { right() } }` is EF105 with the suggestion "Execute this recipe inside the scope", which wraps the whole tail as `run (if flag { left() } else { right() })`. A suggestion is a revision-bound preview that the edited source must pass on recheck: it can expose undeclared rows (EF107/EF108), a still-nested recipe, or a result owned by the closing scope (EF123).

Canonical type positions serialize as bounded references to shared definitions, including nested callable parameters/results and application slots. Keeping a recursive legacy tree beside interned IDs defeats that boundary. Explicitly version the changed inspection schema and retain readable type displays as derived output. Qualify nominal declarations independently from their display names; interface content/version and compiler producer identity remain separate snapshot inputs.

Add ordinary typed function values and explicit finite row parameters together. A reusable helper must preserve its argument's failure/service requirements without a checker branch named after that helper. Instantiate row parameters from argument contracts, support finite union and concrete-label elimination, and reject unsupported ambiguous inference. General conditional type computation and whole-program inference are outside this design.

## Row parameters on service operations and implementation methods

A service operation and the implementation method that satisfies it may declare row parameters, `E: raises` and `R: uses`, with the same inference as ordinary functions: each is solved from the callback argument rows at a direct call, and the operation's result rows are instantiated from the solution (`RowArguments` in inspection). The general callback form is expressible without a checker branch:

```ef
service Server {
    effect fn listen<E: raises, R: uses>(address: string, handler: effect fn(Request) -> Reply raises { E } uses { R }) -> void raises { IoError } uses { R }
}
```

Rules:

- **Rows only.** A type parameter on an operation or implementation method is `EF125`: a Go struct field cannot be generic, whereas rows are erased and cost nothing at the host boundary.
- **Operation `uses` names only row parameters.** A fixed label (`uses { Console }`) is `EF103`: an operation's requirements are what its caller supplies through the callback, never an ambient capability. Construction requirements belong to `impl ... uses { ... }` (see [layers](layers.md)). The call adds the service itself to the caller's row, as for any operation.
- **Conformance is up to renaming.** The implementation method must declare the same number of row parameters in the same kinds and positions (arity or kind mismatch is `EF104`); names are free. Types are compared after identifying the corresponding parameters. The implementation may raise fewer failures than the operation and may not raise a failure the operation does not.
- **Limit: an Effra body cannot absorb an abstract row.** An implementation that runs `handler` raises `E` and uses `R`; it can only forward them, so its method must list `E` in `raises` or fail `EF107`. Catching `E` is `EF125` because recovery of an abstract row needs a row-difference constraint the finite solver does not have. Absorbing `E` into a typed response (the `typed-failure-response` of an HTTP server) is sound only in a trusted host body, which is a later `extern` unit. Consequently a test fake of such a service cannot drive the handler itself; tests call route functions directly.
- **The body is checked against the declared row.** An implementation method may use only the services in its own declared `uses` row (its row parameters included) plus the constructor's concrete captures; using a callback requirement it did not declare is `EF108`, as for a module function. Captures are concrete and are never re-resolved under the method's row binders, so a binder spelled like a captured service neither hides nor widens either.
- Row parameters on operations and impl methods lower exactly as on functions: Go and JavaScript see the callback as an ordinary callable, and the TypeScript declaration of the service and provider type carries the generic row variables.

## Handler soundness regression (historical)

This section records the regression that motivated the function contract; it is resolved. The opaque `Handler` accepted a function requiring a service and lost that requirement when passed through a helper parameter. A public program with `route uses {Users}`, `serveIt(h: Handler) uses {Http}` and `main = run serveIt(route).provide<Http>(LiveHttp)` checked despite missing Users. Independent counsel executed the resulting server and observed a missing-service defect; root independently verified the unchecked requirement in CLI inspection.

Further independent source probes at `4f6aed8` admitted the same missing requirement through `if` selection of a handler and through a record's Handler field, while a direct local alias preserved the requirement. These were distinct acceptance cases for the common representation; a special repair to Http.serve's helper parameter alone was insufficient.

The repair replaced that erasure with the common function contract and diagnoses missing services through the value-flow chain. HTTP handlers are now ordinary `HttpHandler` function values passed to `Http.listen`; `Handler` was removed with `Http.serve` on 2026-10-07. The acceptance list below remains the contract for function values.

Acceptance:

- The missing-Users program rejects before build, including aliases and helper forwarding.
- A function with narrower failures/services can satisfy a declared wider callback contract; the reverse rejects. Check parameters and success types soundly as well.
- Function contracts survive supported locals, parameters, provider configuration and record fields; any unsupported placement diagnoses.
- Forward calls and generic helper composition preserve row contributions. Concrete catch/provide operations remove only their named labels; abstract-label subtraction must be explicitly supported or diagnosed.
- Borrowed input provenance remains distinct from newly acquired invocation results through function calls. Named functions are the first supported values; closures require explicit capture checking before admission.
- Unresolved callback-result provenance remains a deferred callable relation or conservative potential ownership, never harmless unknown. A recipe returned by a callee without a summary (a callable parameter, joined or unresolved evidence, a generic callee) holds whatever it was given and, for an effect callee, whatever it acquired; those held handles belong to the owner running the invocation, for direct calls and recovery handlers alike. A service operation is dispatched to whichever provider is in scope, so it is such a callee too: every managed handle its success may contain, and every handle a recipe it returns may hold, is possibly owned and therefore owned by the owner running it. No provider or service name is an acquisition or borrow proof; a provision that discharges this evidence from a known provider's method summary is a later precision refinement. Paired borrowed/acquired controls cross multiple forwarding levels and declaration-order permutations; supported conditional callees preserve every possible acquisition. A scope inside a generic helper may conservatively diagnose unresolved ownership until a checked obligation model is available.
- CLI/MCP expose the same canonical function/application/row contracts and useful missing-requirement paths.
- Existing source checks, Go/JS behavior and public diagnostics remain truthful. Adversarial nested types and helper fan-out have bounded checking receipts.

## Subsequent reusable data and recovery

First-order type parameters, ordinary generic closed enums and containers should support Option/Result and reusable collections without one compiler case per library type. Retain explicit boundary signatures and supported-layout diagnostics. Pure data outcomes and an effect's execution failure remain distinct; a future Result propagation operator must not silently execute effects.

The owner prohibits nil/null language values. Required fields and callable results contain initialized admitted values; absence uses a closed alternative, including bundled `Option<T>`. Do not add nullable unions, implicit zero-value construction or unchecked `Some` contents when introducing generics or host types. [Absence and host boundaries](absence-and-host-boundaries.md) defines native nil/error adaptation and its separate wire-protocol meaning. Ordinary generic records and closed enums use the common finite template owner, complete application arguments, constructor substitution and exhaustive single-subject match evidence. Bundled Option/Result are ordinary instances of that contract; richer host adaptation and typed recipe containers remain separate implementation obligations.

Multi-subject matching and named variant or-patterns provide reusable state/event decision functions. Diagnose missing pairs, unreachable arms and inconsistent alternative bindings through the ordinary matcher. Keep coverage and type instantiation bounded; exhausting a budget is a diagnostic, never an empty requirement row or a false exhaustiveness proof. Generic data and payload-aware recovery now have explicit Wayfinder tasks because the [machine contract](state-machines.md) needs these ordinary mechanisms.

### Implemented product matches and alternatives

`match a, b { … }` evaluates its subjects once, left to right. Each arm names one pattern cell per subject, separated by commas; a cell lists named-variant alternatives separated by `|`, which binds tighter than the comma: `State.Idle | State.Active { key }, Event.Close => …`. Two real callers chose this spelling: a session state × event step table, and `Data.Option` × `Data.Result` (or a generic `Reply<T>`) absence pairing. It reads like the arm list it replaces, needs no tuple value and keeps the existing variant-pattern syntax. Catch-all cells remain rejected under the closed-data policy.

Alternatives in one cell bind the same names with identical payload types, callable failure and service rows included: rows are never unioned or taken from one alternative, so `A { f } | B { f }` over `effect fn() -> string` and `effect fn() -> string raises {Bad}` payloads is `EF121`. The bound value joins every alternative's payload ownership, captures and callable evidence. Names stay distinct across cells. The checker computes usefulness over closed variant sets (Maranget-style specialization, with variants that select the same arms explored once): missing combinations report declaration-ordered witnesses such as `missing match arm for Session.Closed, Event.Close`, at most eight with an explicit omission notice; unreachable arms and unreachable or duplicate alternatives are `EF117`; binder errors are `EF121`. One work budget (`maxMatchCoverageWork`) covers every question for a match. Exhausting it is `EF137`, which refuses the match without any coverage claim or plan.

The checked first-match plan holds subjects, per-arm cells and binders. Go and JavaScript both lower that plan: subjects into temporaries in order, each tested subject's variant decoded once, then ordered arm tests sharing one emitted body per arm. Neither backend re-derives coverage.

Payload-aware effectful recovery binds declared error fields, eliminates exactly the handled labels and adds the selected handler's rows. Preserve current behavior that a composite cause containing cleanup defects cannot be flattened into a recoverable expected failure. Reifying an outcome requires `Exit` success or failure with its full `Cause`; a four-way success/failure/defect/interruption enum alone loses composite causes and is insufficient.

`recipe.recover<E>(handler)` is the named recovery callback; `catch<E>(value)` stays the constant fallback. A declared error is also its nominal payload type in parameter positions (it is not a stored or returned success value), so the handler is an ordinary function value: a pure `fn(E) -> T` or an `effect fn(E) -> T raises {F} uses {S}`. Its parameter must accept exactly E and its result must be assignable to the recipe's success. The recovered recipe carries `(failures - E) + F` and `services + S`. Its result ownership and field evidence join the original result with the handler's invocation result, so an acquiring handler cannot make a borrowed result, or a stored recipe in its fields, escape a closing scope; a handler without a named summary leaves the field evidence unknown. Handles inside the bound payload keep the owners they had in the failing execution: a handle the failing layer acquired is owned by whichever owner runs the recovered recipe, and a handle owned by a scope, provision, timeout or child that closed while the failure propagated stays owned by that closed owner. The handler is checked against the payload handles it dereferences, so a handler that reads a closed handle is refused at the `recover`, while one that discards the payload, or keeps it without reading it, is admitted; a kept handle carries its owner, and its later use is checked where it happens. A payload of a callee without a summary is unknown evidence, never an empty proof. Recovering a stored recipe builds a new recipe and runs neither the work nor the handler. Only a solitary typed E failure reaches the handler. Defects, interruption, several failures and failures combined with cleanup defects propagate with their complete cause on Go and JS. Builtin failures such as Timeout have no declared payload and are handled with `catch`. Reified `Exit` remains unexposed.

Scoped acquisition must make acquisition plus finalizer registration cancellation-safe. Its surface should use the common typed-function/library interface where that is sufficient; a new keyword needs evidence that the ordinary interface cannot express the invariant. Provider sharing should remain explicit through recipes and materialized values; fallible acquisition needs rollback and completed release, and its failure-retention policy cannot be inferred from a generic memoization name.

These are finite next implementation contracts, not claims that collections, effectful recovery, public acquisition or fallible shared providers already exist. Each needs its own source cases, negative tests, both-target matrix and upstream behavior mapping before closure.

## Pipe operator

Status: shipped notation (2026-10-08, lane P1). `x |> f(args)` is `f(x, args)`: the piped value is positional argument 1, so it always fills the first declared parameter. The rewrite happens in the parser, before binding or checking, so the checker and both emitters see an ordinary call. The compiled output equals the hand-nested program's, apart from the source-revision line and the source positions that follow an edited byte offset (see Construct status for what the equivalence gate compares). The [pipe example](../../examples/pipe.ef) shows each rule below.

```
Postfix  := Primary { "." Name | TypeArgs | "(" Args ")" | Fields | "|>" PipeCall }
PipeCall := Name { "." Name } [ TypeArgs ] "(" [ Args ] ")"
```

- **Form.** The right side is a static name path followed by exactly one argument list. A bare `x |> f`, a parenthesised callee, a keyword form such as `run g()` and a literal are EF002; the bare case is anchored at `f` and says `write f()`. There is no placeholder, last-argument or bare-function form, so there is one canonical spelling and the arity is always visible.
- **Associativity.** `x |> f() |> g(b)` is `g(f(x), b)`. After the call the chain continues on the result: `x |> f().len` is `f(x).len`. The `.` after `|>` starts a path, so `x |> M.timeout(ms: 5)` is an ordinary call to `M.timeout`, not the postfix `.timeout` intrinsic. This is a deliberate exception to "the ordinary call the author wrote": the nested spellings `S.timeout(x)`, `S.orFail()`, `S.provide(...)` and `S.catch<...>(...)` parse as the method intrinsics after any receiver, so a service operation with one of those names is unreachable by nested call but reachable by `x |> S.timeout()`. Tests pin both readings. The admitted dot-method lanes (DOT0-DOT6, decided 2026-10-08) make `.catch`, `.provide`, `.timeout` and `.orFail` ordinary `effra/effect` methods and remove the intrinsics, and this exception with them.
- **Precedence.** `|>` is in the postfix chain with `.`, call and type application. `run` and `fork` take the whole chain: `run x |> f()` is `run f(x)`, and `(run x) |> f()` pipes the result. This matches the existing `run r.timeout(5)` reading and makes the intrinsic-to-pipe rewrite a local token substitution.
- **Binary operators.** A pipe chain beside `+`, `-`, `*`, `/`, `%`, `<`, `<=`, `>`, `>=` or `==` without parentheses is an EF002 at the `|>`, so `a + b |> f()` is never silently read one way or the other. Effra's `+` is string concatenation or signed i64 addition, and the languages split on it. Gleam's string `<>` binds looser than its pipe, so `a <> b |> f` is `a <> f(b)`, while its numeric `+` binds tighter, giving `f(a + b)`. Elixir's `<>` binds tighter than `|>` (`f(a <> b)`), and ReScript's `++` is looser than `->` (`a ++ f(b)`). The `==` refusal is a conservative owner choice, not an ambiguity fix: Elixir, Gleam and ReScript all read `a |> f() == b` as `f(a) == b`, and Effra costs the parentheses in `if x |> f() == y` to keep one rule for every binary operator. Write `(a |> f()) + b` or `a + (b |> f())`. A test fails if a binary operator is added without a recorded decision about the pipe.
- **Named arguments.** Positional arguments precede labels, so prepending the piped value is always well formed: `x |> wrap(open: "<", close: ">")` is `wrap(x, open: "<", close: ">")`. Labelling the first parameter is EF106 "the piped value already binds parameter text; remove label text". A callee without parameters is EF106 at the `|>`. A recipe piped into an ordinary parameter, as in `run load() |> shout()`, adds the hint that `|>` binds inside `run`.
- **Evaluation.** The callee evaluates nothing and the piped value is written first, so source order is evaluation order and the pipe adds no temporary or closure. (A call that reorders labels already lowers through an argument adapter; piped or nested, the adapter is the same.)
- **Tooling.** `Expr.PipeSpan` records the `|>` token for diagnostics, which read it for wording and anchors only; acceptance, checking and emission never do, and a test pins that by erasing it. The formatter keeps the author's breaks, indents each line-leading `|>` one continuation level and spaces the operator.
- **Library convention: the subject comes first.** Bundled and user APIs that are meant to be piped put the value they transform in the first parameter, as Elixir, Gleam and Effect's data-first forms do. No language rule enforces it. Parameter names remain public API through labels. Receiver methods (lanes DOT0-DOT6) are the dot spelling of the same call: `u.m(x)` is `User.m(u, x)` is `u |> User.m(x)`, with the receiver as the subject.

Equivalence gate: the differential rewrites every static-callee call with a positional first argument in the `.ef` files and Go-test programs into pipe form, except calls that hold a comment, label the first argument, parenthesise the callee or are already piped. It compares each target's compiled artifacts and statuses: JS entry, library, `.d.mts` declarations and test emission, and Go build and test emission, with rejection codes. Two source-position patterns are masked (layer binding node IDs and Go NodeSpec positions); a control proves nothing else is. A control that appends the piped value last must fail it.

## Constant parameter defaults

Status: declaration admission shipped in DEF1; checked call binding (B2) shipped 2026-10-09. A parameter may declare `name: T = VALUE` where `VALUE` is an i64, string or bool literal or an admitted constant alias, checked against `T` and published in canonical signatures, inspection, interface summaries and formatting (DEF1). Implementation methods never own a default; the service declaration does. Budgets and codec bounds stay `required` choices and cannot take one.

Call binding is checked call-site sugar over the ordinary call:

- **Binding.** Positional arguments fill parameters from the left and labels bind by name, exactly as without defaults. A parameter left without an argument binds its declared constant when it has one; otherwise the call is EF106 `missing argument for parameter NAME`. A positional call cannot skip a parameter, so `gap(5)` with `gap(a: i64 = 1, b: i64)` binds `a` and still misses `b`; write `gap(b: 5)`. A required-choice parameter has no default and is always written. The piped value is positional argument 1, so `x |> render(loud: true)` omits the same parameters as `render(x, loud: true)`.
- **Lowering.** The checker places the constant's checked literal in the omitted parameter's slot of the call's bound argument vector (`Expr.BoundArguments`), before the first authored argument that binds a later parameter; authored `Args` stay untouched for tooling. Constants evaluate nothing, so authored arguments still run once, in source order, and a call whose labels bind parameters in increasing order becomes the plain positional call. `render("b", loud: true)` therefore compiles to exactly `render("b", "!", 7, true)` on both targets, and a call whose labels reorder authored arguments keeps the existing adapter with the constants passed through it in their slots. A negative i64 default is one signed literal (`-3n`, `int64(-3)`), as in a constant declaration, rather than the runtime negation an authored `-3` lowers to.
- **One checked call.** Generic and row inference, ownership, callback policies and the application identity see the complete parameter vector, so an omitted call is an application of the callee's declaration identity, including an imported one such as `Fns.suffixed`, to the same arguments as its explicit spelling. No callee-side parameter initializer or presence check is emitted on either target: every default expands at each call site that omits it, recursive calls included. Direct self tail calls that omit a defaulted parameter are loops like any other; the constant is assigned to its slot on every iteration.
- **Not a value-level default.** Callable values and function values keep their full declared arity: `let f = render` then `f("a")`, or passing `render` where `fn(string) -> string` is expected, is EF106. There is no eta-expansion or partial application.
- **Honest ABI.** Generated TypeScript declares every parameter required with its declared type. JavaScript callers pass every argument, and `undefined` is not a default marker. A strict TypeScript consumer test pins that `render("a")` is an error. A default is part of the callee's public contract (DEF1 interface identity), but it never appears in the callee's emitted body: changing it changes only the omitting callers' emitted calls, and programs that spell every argument compile identically.

Evidence: `internal/compiler/parameter_default_calls_test.go` compares every emitted artifact (JS entry, library, declarations, Go build) of a program that omits arguments with one that writes the constants, across an ordinary function, a compiler-distributed import, a service operation, a pipe and a row-polymorphic effect function with an empty row, runs both targets, and keeps controls showing that a different constant or a trailing-label adapter is observed as a different call. It also pins source-order evaluation of reordered effectful arguments, the refusals above, stale-default controls, and the defaulted self-tail loop with a mutant that keeps the previous iteration's value in the omitted slot. A second differential instantiates a row-polymorphic callee with non-empty `raises` and `uses` rows. Type-parameter substitution through a defaulted call is not claimed while user generic functions are refused (EF127); only row substitution is exercised.

Identity versions: none changed. Every program accepted before B2 compiles byte-identically, and an omitted call's output is an existing explicit call's output; DEF1 already versioned the declaration facts (semantic and graph schema 8, interface summary 4, checker ABI 9).

## Performance and restraint

### Zero-cost abstraction obligation

Strong abstractions are a destination obligation alongside fast compilation and
small executables. An admitted construct must make the illegal states and
invalid operations covered by its checked contract unrepresentable in checked
Effra source, while foreign and trusted behavior remains explicitly qualified,
without weakening its checked failures, service rows, ownership, cancellation
or completed cleanup. Its cost unit is a semantic
equivalence baseline: the Effra caller, an explicit Go caller and an explicit
TypeScript/Effect caller perform the same validation and observable work under
the same ownership/lifetime policy.

The implementation records whether the abstraction is erased, directly lowered
or retained behind a runtime representation. Matched receipts expose emitted
source, retained modules, executable bytes, allocations, dispatch and residual
checks. A candidate with unexplained abstraction-only cost remains unresolved;
neither an unequal fixture nor a weakened guardrail is a zero-cost result. The
Rust iterator, C++ Per.7/Per.11/P.9/Per.6 and Go compiler/escape-analysis comparisons in
[`PRIOR_ARTS.md`](../../PRIOR_ARTS.md#zero-cost-abstraction-comparison-2026-10-08)
are primary constraints and counterevidence, not a universal Effra claim.

The native Go acceptance control is optimized idiomatic Go performing the same
validation, failure/service rows, ownership, cancellation and completed cleanup.
The native target must match or beat that control on a matched workload; a
slower or inconclusive result remains unresolved. The JS target must pursue
every material measurable lowering or specialization opportunity, including
static `match` dispatch to `if`/`switch`, direct calls, join-point sharing and
generated effect-runtime paths where the emitted code benefits. Such generated
code may be machine-written rather than human-style source, but it preserves
the pinned default Effect-compatible ABI and userland runtime contract. A
many-times speedup is an ambition to test, not a current result or promise.

Measure canonical checking, import reuse, emission and generated runtime separately. Compare enum representations on matched codec/server workloads before changing them; an interface representation is not automatically slower and a flattened variant struct can waste space. Keep raw losing results. Avoid renaming established syntax merely to anticipate an unused feature; introduce data-method syntax only with real callers.

The [native server specification](native-server-contracts.md) consumes these mechanisms. Routing, retry, caching, queues and RPC framing remain library policies behind ordinary checked interfaces. No route-specific syntax, implicit dependency search or unchecked host conversions are introduced by this spec.
