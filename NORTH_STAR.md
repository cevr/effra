# North star

Ergo is becoming a general application language, for servers and front-ends, that preserves Go-like simplicity and fast native builds, makes Effect-style contracts and owned lifetimes explicit, and adds algebraic data types and useful abstractions in the spirit of Borgo. Straightforward host interop and compiler-backed inspection serve both humans and agents. `.ef` is its source format; `ergo` is its command.

The owner reaffirmed this balance on 2026-10-06. Simplicity means a small set of regular concepts, readable local control flow and predictable costs; it does not mean removing abstractions and making every application repeat their implementation. Effect-grade guarantees require executable evidence for typed failures, dependencies, cancellation and completed cleanup, with unsupported and foreign behavior clearly distinguished.

## Go is the only target (owner, 2026-10-26)

Owner, 2026-10-26: "we're removing the js interop id say". And: "this will be effect for Go with this kind of new language as well. So we'll have a standard library and all the things that Effect does kind of more but more tailored to this new language and the new idioms". Go is therefore Ergo's only target. Effect stays prior art for the guarantees (pillar 2 below). It is no longer a runtime, an ABI or a conformance dependency: the JavaScript emitter, the pinned Effect checkout and the Node toolchain are removed, and `--target js` is the EF110 diagnostic. The standard library covers what Effect does, restated in Ergo's idioms rather than ported API for API. The same day the owner dropped the exact Bun version check and the pinned Effect upstream requirement ("and lets remove this requirement"; "also the effect requirement as well").

This supersedes every earlier direction in this file that names a JavaScript or TypeScript target, front-end code through that target, the pinned Effect runtime or ABI, or TypeScript/Effect baselines. Each such passage is marked "superseded 2026-10-26" and kept as a record of the earlier direction.

## North-star pillars (owner, 2026-10-26)

Owner, 2026-10-26: "what I want as a North Star is traceability, you know, observability. The core guarantees of effect and simplicity of go, laws and proofs for sure. The same kind of error and dependency tracking that effect gives, and also really strong focus on agent interpretability, like that they can really understand the code and interact with it that's different than languages that have come before it."

Owner, 2026-10-26, on performance: "zero cost subtractions [abstractions] is very important and being able to compile down to optimized code that's even faster than hand optimized Go code".

1. Traceability and observability.
2. Effect's core guarantees.
3. Go simplicity.
4. Laws and proofs.
5. Error and dependency tracking.
6. Agent interpretability.
7. Performance: every construct lowers to code no slower than hand-written Go, and a feature that is not used costs nothing. Beat hand-optimized Go where the language knows facts Go cannot. Claims need measured evidence.

Score every construct and spike against all seven pillars. Observability and agent interpretability are language concerns, not tooling afterthoughts. Pillar 4 names proofs, so the earlier "no proofs" position on laws is re-opened rather than closed; until a proof tier is designed, a passing finite law suite is still reported as tested, never as proved.

## Owner direction before 2026-10-26

The directions below keep their dates. Passages marked "superseded 2026-10-26" yield to the two sections above.

Owner direction added 2026-10-08: strong abstractions and zero-cost implementations
are a joint destination. A higher-level Ergo construct must make the illegal
states and invalid operations covered by its checked contract unrepresentable in
checked Ergo source, while foreign and trusted behavior remains explicitly
qualified. It must preserve the same validation, ownership, cancellation and
cleanup contracts as an explicit implementation. Its admitted uses should erase
or lower directly enough that abstraction-induced executable size, allocation,
dispatch and residual-check costs are visible and measured against semantically
equivalent explicit Go and TypeScript/Effect baselines. This is an acceptance
obligation, not a claim that current lowering has zero overhead or that every
abstraction can be universally free. **Superseded 2026-10-26** in part: the
TypeScript/Effect baseline went with the JavaScript target; the baseline is
semantically equivalent explicit Go.

Owner performance direction added 2026-10-08: a compiled native Go application
must meet or exceed an optimized idiomatic Go application on a matched workload
when both preserve the same validation, failure/service rows, ownership,
cancellation and completed cleanup. This is a destination acceptance target, not
a current result. The JS target must pursue every measurable lowering and
specialization opportunity in its admitted hot paths, including static `match`
dispatch to `if`/`switch` forms when the generated result is better. A generated
or specialized effect runtime may be machine-written in a form a human would
not choose, and a many-times speedup may be a useful hypothesis to test, while
the pinned default Effect-compatible JS ABI and userland runtime contract remain
intact. These are measured ambitions, never a universal multiplier or a reason
to weaken errors, scopes, cancellation or completed cleanup. **Superseded 2026-10-26** in
part: the JS target and its pinned Effect-compatible ABI are removed. The native
Go clause stands, and the lowering and specialization ambition, including a
generated runtime, now applies to Go.

Additional owner direction, 2026-10-06: state machines are a vital primitive and should be straightforward to express and inspect at language level. Compare Effect Machine and XState before fixing the supported transition/lifecycle contract. Rust-style derivation should remove structural codec boilerplate while retaining Effect-style transformations between distinct wire and domain types, including explicit failures and service requirements in each direction. Compare Gleam, ReScript and TypeScript for host-language compilation and interop. These are implementation requirements under research, not claims of current support.

The owner sharpened the priority on the same date: keep Ergo as Go-like as possible—simple and explicit, adding the capabilities Go forgoes. XState v6's active PR/branch is the main machine prior art; v5 is historical comparison only. New primitives reuse ordinary data, functions, effect rows and scopes. Common source should not require a framework vocabulary, a separate schema declaration for every type, or a tuple of type-level bookkeeping parameters just to call a library.

Owner loop direction, 2026-10-06: actively seek useful primitives that make writing Effect explicit, declarative and delightful. Every pass traces recurring production ceremony, identifies the underlying contract, and compares a small regular primitive against ordinary library composition. Prove adopted improvements with two unrelated runnable callers and negative controls: shorter wiring must retain visible execution, failures, services and owners. Readability and inspectability are acceptance criteria; line-count reduction alone is not evidence. Research sketches remain proposals until they execute on their advertised targets.

Owner layer direction, 2026-10-06: make `layer` a first-class declaration composing `service` operations and `impl` behavior/construction. The language assembles a checked lazy acquisition graph; the runtime owns shared acquisition, rollback and completed cleanup. Infer exposed `provides`, construction `raises` and remaining `uses`; checked annotations may narrow outputs or bound rows. Bindings, rather than graph leaves, determine an unannotated layer's exposed services. Merge by node identity, diagnose ordinary duplicates, replace deliberately before acquisition, and provide once at an execution boundary. Domain functions retain requirements. See [layer contracts](docs/specs/layers.md); this is authorized implementation work, not current layer support.

The owner further clarified that machine steps must be allowed to be effectful. Admit both ordinary pure and effect functions with explicit contracts; serialize their execution under the actor's owner, preserve failure/service rows, and commit state only after successful evaluation and cleanup. Local state commit does not imply rollback of external effects.

Owner machine direction, 2026-10-07, 2026-10-08 and 2026-10-09: "if we're adding a special compile check for machines, then it should be a language construct rather than just api"; on 2026-10-09: "one thing about the machine spec, Step is a parser intrinsic? how can we make it so users can provide their own machine runtimes?". `machine` is therefore a visible construct, and it is provider-independent: a construct that any userland runtime can provide. The compiler checks the declaration and lowers it to a provider-independent machine plan. An ordinary userland provider owns execution, admission, scopes, cleanup and observation, and the compiler never dispatches to a built-in machine engine. Ergo ships its own userland machine runtime as the first provider; it uses only the public provider boundary that any second provider could use. See the [machine provider contract](docs/specs/machine-provider-contract.md). This is authorized implementation direction, not current provider support.

Owner construct direction, 2026-10-09: "i think in the case of machines, syntax is preferred over special cased library constructs" — "and generally i should say all of our langauge constructs". Whenever the compiler must know a construct's meaning, for checking, inference, plan facts, inspection or special lowering, that construct is syntax: a keyword, operator, declaration form, postfix construct or predeclared language identifier defined by the language (Go's predeclared `len` and `error` model). It is never a bundled or prelude library item that the compiler recognises by identity or name to grant language semantics, which is the Rust "lang item" pattern. Library code the compiler treats exactly like user code stays library; an item becomes library by losing every compiler branch, not by moving its declaration. A library intrinsic, which swaps the implementation of an ordinary declared signature without changing diagnostics, types, rows or ownership, is a separate permitted category and must be documented; so is the implementation of a syntax construct. A language protocol, a row label whose charging a construct's own rule defines (such as `Foreign` for host calls), is language; an ordinary capability service stays library. Foreign identities that `import go` adapts, such as `context.Context`, form that construct's finite host-protocol table. This sharpens the 2026-10-07 [visible-construct refinement](docs/design.md#language-design-principles) and supersedes the earlier plan to turn `.catch` and `.provide` into ordinary library operations: they are dedicated parser forms today, and they stay syntax. Two parts of this paragraph are superseded by later direction. First, "they stay syntax" no longer holds as stated. The [effect rows note](docs/research/effect-rows-as-types.md#verdict) ([#115](https://github.com/cevr/ergo/issues/115)) finds `.catch<E>` and `.provide<S>` GO as ordinary library through general row features, each gated on its unit ([#128](https://github.com/cevr/ergo/issues/128), [#131](https://github.com/cevr/ergo/issues/131), [#132](https://github.com/cevr/ergo/issues/132)). It finds `.recover<E>` conditional ([#133](https://github.com/cevr/ergo/issues/133)) and `.timeout` and `.provide(Layer)` NO-GO as library. Second, the 2026-10-12 construct bar below no longer admits a postfix construct as a construct spelling. [#134](https://github.com/cevr/ergo/issues/134) is re-deciding provide and timeout, including whether one provide block absorbs `.provide<S>`. Until those units land, every form named here remains a dedicated parser form. The [compiler-known constructs audit](docs/research/compiler-known-constructs-audit.md) inventories current and planned violations and their migrations; it is direction, not a claim that they are fixed.

Owner runtime direction, 2026-10-08 and 2026-10-12: userland should be able to provide a superior effect runtime, and Ergo intends to supply one: possibly a generated runtime that no one would write by hand, keeping the same guarantees while running many times faster. The language exposes checked constructs and a lawful runtime contract; a runtime is an ordinary provider of that contract, selected visibly, in the same way JSX notation selects a user-defined pragma instead of a framework adapter. Until a scoped, reviewed provider decision admits another representation, the JS ABI stays pinned and Effect-compatible and pinned Effect remains the default and reference provider. Provider laws and evidence categories live in the [lawful runtime contract](docs/research/lawful-runtime-contract.md). The speedup is a measured ambition under the performance direction above, not a current result. **Superseded 2026-10-26** in part: there is no JS ABI and no pinned Effect provider. Ergo's own Go runtime is the first provider, and a lighter or generated provider joins through the same lawful contract.

On 2026-10-12 the owner set the admission bar: "it should probably downlevel to effect code, but if we can make a lighter runtime that has the same guarantees as effect, that might be an interesting avenue, but it would have to [pass] the same test suite as [Effect]." Then: "it doesn't have to have the same contract … it would be the same laws, I suppose, I would have to follow. So it would be an approximation. … we should put [it] up the queue because it's part of the language constructs." The JS target therefore keeps emitting pinned Effect as the default and reference provider. A lighter provider is admitted by the same laws, the RS1 suite over P1–P12 and R1–R15 ([#124](https://github.com/cevr/ergo/issues/124)), together with the Ergo conformance corpus. Those laws define what scope, fork, join, interrupt, timeout, recover, provide and layers mean, so they belong to the language-construct tier. A provider's representation and API may differ from Effect's. Pinned Effect's own test suite ([#123](https://github.com/cevr/ergo/issues/123)) is secondary evidence that approximates the laws. A provider that claims an Effect surface keeps that suite's compatibility evidence for the surface, but the suite never admits a provider alone. The RS1 suite does not run yet, nothing runs the Effect suite against a second provider, and a provider's performance is measured only after admission. **Superseded 2026-10-26** in part: Ergo no longer downlevels to Effect code, and no target emits pinned Effect. The laws stay the admission bar for every provider, including Ergo's own Go runtime; Effect's suite stays approximation evidence for the guarantees only.

Owner application direction, 2026-10-11: "I definitely say [Go's] simplicity is the goal. We want to compile down [to] typescript." And: "I think a goal is that we should be able to swap out the provided effect runtime for user [land] implementation that could potentially be better, for example, or other kind of monadic abstractions for different use cases … And something that can really be fast. … I'd say, for now, it's definitely not just a server programming language. This could be app, basically application code, whether server or front-end, because we can compile the typescript. So anything JavaScript can handle, we should be able to handle, too. So, this is, like, rendering [three.js], all these kinds of things, canvas, [WebGL] … But just with more guardrails. and kind of IO being handled by effects rather than promise based run times." Ergo is therefore a general application language, for servers and front-ends, and this widens the 2026-10-05 server scope. Native Go stays the default executable target. The TypeScript/JavaScript target on Effect carries front-end code, with I/O handled by checked effects instead of promises. Go's simplicity stays the reading standard even where the output is TypeScript. A userland provider may replace the bundled effect runtime under the runtime direction above, and other monadic abstractions are tracked as generalized `run` binding ([#73](https://github.com/cevr/ergo/issues/73)). [#117](https://github.com/cevr/ergo/issues/117) tracks the gaps between today's server-focused profile and real-time client code: floating-point numbers, loops and local mutation, typed numeric buffers and a render-loop spike. None of them is built, so front-end support is direction, not a current claim. **Superseded 2026-10-26** in part: the TypeScript/JavaScript target, and front-end code through it, are removed; Go is the only target. Go's simplicity as the reading standard and replaceable userland providers stand.

Owner law direction, 2026-10-12: "laws are not just for runtimes … they also help to kind of formalize and prove behaviour more than types can … kind of like ghosts of departed proofs and bend … we should consider that." And: "laws is for sure a construct." A law is therefore one general construct that states and checks behavior types cannot express. It has many clients: runtime providers (R1–R15, [#124](https://github.com/cevr/ergo/issues/124)), equality and ordering dictionaries, codec round-trips, service operations, machine invariants and Ghosts of Departed Proofs evidence at opaque ingress. This confirms the 2026-10-08 `law`/`contract` decision in the [design principles](docs/design.md#language-design-principles) and settles the placement that the [lawful runtime contract](docs/research/lawful-runtime-contract.md) left open. The [#125](https://github.com/cevr/ergo/issues/125) spike decides the construct's shape, discharge and inspection, not whether laws are a construct. A passing finite law suite is reported as tested, never as proved. No law construct is implemented.

Owner construct bar, 2026-10-12: "if we're gonna have language constructs, they should be distinct from other already possible constructs. Like normal dot chaining and whatnot." On keywords and primitives: "I think the else block is overloading if else, since that's already a well-known programming concept. … scope and all these things are actually just normal methods in typescript effect. Time out, I look at it as just part of a schedule and whatnot. So I'm wondering why they need to be Language constructs. I mean, if we can justify it, it makes sense, but we'd have to think about a good way to make them primitive rather than blocks." And: "the goal is to provide a language that has enough guardrails so that bad code or illegal states cannot be represented. And that's really where machine as a language construct earns its keep … layers … So if we can make these language constructs and they make sense, then I think we should. But they need to be designed in a way that really makes sense and that are portable across different domains. So [userland] implementations of various different things that may not necessarily be effect runtimes, but are effectual … may not be the default standard library that we provide, but it could have a [userland] implementation that is superior in whatever domain they're in."

The recorded synthesis of these three directions, not owner words, follows. A construct earns its place by passing the guardrail test and the portability test, both defined in the [glossary](GLOSSARY.md); its protocol's laws come from [#125](https://github.com/cevr/ergo/issues/125). Where the guardrail test fails, the behavior is a primitive function with honest rows plus library, as in Effect. A construct that passes both tests uses a keyword or block form distinct from dot and pipe. A dot or pipe form is always ordinary library, and no well-known keyword is reused with a new meaning. Machines already follow this through provider-independent plans. [#134](https://github.com/cevr/ergo/issues/134) decides, for `.provide`, `.timeout` and `.orFail`, between a keyword or block construct and ordinary library, and it replaces [#95](https://github.com/cevr/ergo/issues/95)'s plan to reserve postfix words. Until #134 decides, those forms remain postfix constructs. Of the compile-to-host peers in the [compiler-known construct comparison](PRIOR_ART.md#compiler-known-construct-comparison-2026-10-09), Elixir's fixed special forms over library functions are the closest match for this bar.

On generics: "I feel like the language design is leading more typescript than go, especially with the generics … they look very expressive. Owner composability direction, 2026-10-12: "very important to think about composability … the primitives have to be able to be stacked on top of each other and grow together … effect does that pretty well in typescript … well organized that they can build into greater and greater sums that are gooder than its parts." The recorded elaboration of this direction, not owner words, is that every construct and primitive decision runs the [composability checks](GLOSSARY.md) with evidence: lossless wrapping, nesting, first-class recipes, orthogonality and composition laws ([#125](https://github.com/cevr/ergo/issues/125)). A visually distinct construct must still pass these checks. In the [effect rows note](docs/research/effect-rows-as-types.md#verdict), a prototype of the recipe-parameter contract checks user wrappers of catch, provide and timeout like the direct forms on nearly all of the corpus. A wrapper that closes its own scope around the wrapped work is not yet shown, and the contract is not implemented ([#128](https://github.com/cevr/ergo/issues/128)).

Small binaries are another owner-established north star, 2026-10-06. Keep unused standard-library and runtime facilities out of application executables, including when a fluent API is used. Library availability in the distribution must remain separate from application retention, while a user-declared foreign Go import is a required package-initialization dependency rather than an unused facility; module selection, initialization and direct-call lowering need measured size and reachability evidence.

Owner interop constraint, 2026-10-06: preserve the standard protocols that make Go libraries compose. Automatically import native type identities, methods and structural interfaces such as readers, writers, closers, filesystems and contexts, while retaining native values and useful optional method sets. Signature compatibility is distinct from resource ownership, cancellation, shared mutation and behavioral trust. The [language/library partition](docs/research/effect-language-boundary.md) keeps checked Effect contracts in regular language mechanisms and facility policies in modules; broader host objects and methods remain implementation work.

Owner data constraint, 2026-10-06: Ergo has no `nil` or `null` language value, nullable ordinary type or observable uninitialized field. Absence is an explicit closed alternative, with bundled `Option<T>` supplied by the generic-data contract. Nullable host results adapt at the boundary; a native nil pointer cannot become `Some` of an ordinary host reference. Preserve Go's error and partial-result semantics, including a nonnil error interface with a nil dynamic payload. Native runtime internals and wire protocols may contain null representations without exposing them as an unchecked Ergo value. See [absence and host boundaries](docs/specs/absence-and-host-boundaries.md). Wider host adaptation remains implementation work.

Actor direction under consideration, owner question 2026-10-06: compare BEAM/OTP supervision and hot code loading, Effect Cluster, celld, Rivet and Cloudflare Durable Objects. The [research](docs/research/actor-model-and-durability.md) recommends checked local actor ownership and explicit supervision, with durable entities and workflow replay supplied by optional providers/libraries. Preserve native Go builds and exclude unused actor/storage/deployment modules from application retention. Shared mutable host values, process failure, ambiguous external effects and code upgrade boundaries must remain explicit. This comparison does not expand the first machine profile into distributed execution or certify those guarantees; a later finite contract and executable conformance are required.

Owner refinement, 2026-10-06: actors are owned addressable behavior, not necessarily machines. Actor execution primarily belongs to runtime/stdlib and reuses ordinary service/impl/effect/uses/raises/scope contracts. Typed handlers and restricted receive loops are useful without a new declaration. Machines add transitions and entry lifetimes; message-free effects remain fibers. Supervision, durable addressing and persistence compose with either behavior independently. The [actor contract](docs/specs/actors.md) resolves the proposed initial payload/host-alias, acknowledgement and inspection boundaries; syntax must earn a guarantee common mechanisms cannot express. Source review is input, not local/distributed runtime proof.

Syntax naming follows the owner's 2026-10-06 clarification: expected failure rows use `raises`, alongside service `uses` rows. Replace the earlier `throws` keyword consistently in admitted source, examples, diagnostics and tooling documentation. Keep naming idiomatic and regular; this spelling change does not alter typed failures, defects or cancellation semantics.

The canonical no-value contract is `void`: the `void` type and bare `void` expression describe successful completion without an information-bearing result. Empty parameter and argument lists remain `()`, while `()` is rejected as a type or expression so no-value syntax cannot be confused with grouping or calls. `void` is not absence, `never`, nil, null, or a backend sentinel; `Option<void>` retains its `Some`/`None` distinction. The Go target may use a zero-size carrier in value positions, but that representation does not change the source contract.

Tooling must expose editor-grade diagnostics and full types through the CLI and MCP as well as the language server (owner, 2026-10-06). Errors, warnings and advice retain their severity, source ranges and checked revision across surfaces. Full types include data structure, callable contracts, dependencies and available ownership evidence; a display name alone is insufficient. Bounded references preserve complete type identities without recursively expanding entire programs. See the [shared tooling contract](docs/specs/semantic-tooling.md); this is a requirement, not a claim that the editor adapter is implemented.

The owner also requires user-defined lint rules (2026-10-06). Ship a versioned, inspectable extension API over the same compiler facts, with configurable rule packs, meaningful source-based tests and shared CLI/MCP/LSP reporting. Project policy may add advice or fail a lint gate; it cannot suppress compiler correctness diagnostics or alter checked types. Optional rule execution must not enlarge application binaries or become a mandatory build dependency. See [custom lint rules](docs/specs/custom-lint.md).

The owner requires a built-in formatter (2026-10-06). One canonical `.ef` style and shared printer serve `ergo fmt`, CI checks, MCP previews and editor formatting. Preserve comments and directive meaning; formatting needs syntax, not successful typechecking or backend execution. See the [formatting contract](docs/specs/formatting.md). The pure formatter and shared traversal are integrated at `45b43d2`; CLI/MCP adapters are integrated and exercised through real processes, and LSP document formatting uses the same formatter over versioned buffers, pending independent review.

## Tiebreaks

- **Structural correctness** beats **fast move-in-place** (owner AGENTS.md, 2026-10-05): deliver coherent changes in compiling units; reject shortcuts that hide ownership or duplicate authoritative semantics.
- **Explicit contracts** beat **terse syntax** (drafted 2026-10-05): reject shorter syntax that hides a requirement, target restriction, or foreign trust assertion.
- **Truthful target limits** beat **feature parity** (drafted 2026-10-05): diagnose unsupported operations until an adapter proves their contract.
- **Completed owned cleanup** beats **deadline punctuality** (drafted 2026-10-05): a managed timeout may exceed its deadline while waiting for cooperative shutdown; early return requires an explicit surviving owner.
- **A small regular language with deep libraries** beats **one-to-one API syntax** (owner direction applied 2026-10-06): adopt shared type/function/module mechanisms before adding a special compiler operation for each Effect combinator. Shorter source is useful when control flow and contracts stay visible.
- **Measured implementation evidence** beats **familiar API names** (owner direction applied 2026-10-06): upstream tests guide behavior, but copied tests and similarly named functions cannot establish parity. Preserve slower results and unsupported cases in receipts.
- **Strong abstractions with visible zero-cost obligations** beat **repeated hand-written ceremony** (owner direction applied 2026-10-08): compare the same validation, ownership, cancellation and cleanup in an Ergo candidate and an optimized idiomatic Go control (the TypeScript/Effect control went with the JavaScript target, 2026-10-26). Erasure or direct lowering is valuable only when residual allocation, dispatch, checks, retention, executable size and runtime cost are measured; a failed or unmeasured candidate remains unresolved.
- **Contract guardrails** beat **zero-cost slogans** (owner direction applied 2026-10-08): never remove a check, row, owner or cleanup step to make an abstraction appear free. Rust iterator examples, C++ Per.7 design-for-optimization, Per.11 compile-time lowering, P.9 safety-cost and Per.6 measurement guidance, and Go escape analysis are primary comparisons, not universal Ergo proof.
- **Measured target parity** beats **a convenient weak baseline** (owner direction applied 2026-10-08): native Go uses optimized idiomatic Go with the same contract, and Go lowering investigates static match lowering, direct dispatch and generated/specialized effect runtime paths. A possible many-times speedup is a testable ambition, and losing candidates remain visible.
- **One inspectable contract** beats **duplicated declarations** (owner direction applied 2026-10-06): derive structural codecs from checked data and project machine graphs from checked transitions; retain explicit representation, transformation and lifecycle policies. Automatic derivation does not prove a transformation reversible, host data valid, or a machine durable.
- **Go-like local readability** beats **framework API fidelity** (owner clarification, 2026-10-06): use ordinary statements, typed functions and explicit execution for behavior; keep declarative additions small and inspection rich. Adopt proven guarantees without reproducing every upstream combinator, builder or configuration concept in source syntax.
- **Go idioms** beat **novel notation** as the default lens (owner, 2026-10-08: "go idioms are key in terms of simple yet expressive"): start from the Go spelling and shape, and depart only when a recorded decision shows the departure serves a north star better. The owner may override a Go spelling decision by decision; explicit `pub` replacing Go's capitalized exports is one such override (owner, 2026-10-08). **Superseded 2026-10-27:** asked again with the recommendation to export by Go's capitalisation, the owner answered "Yeah, let's go with your [recommendations]", so exports follow Go's capitalisation and `pub` is withdrawn ([spec grammar](docs/spec/grammar.md#visibility)).
- **Reconsidering a prior** beats **consistency with it** when the change better serves these north stars (owner, 2026-10-08: "always reconsider priors if it better serves our north stars"): a settled spelling, admission or design reopens on new evidence; record the superseded choice and the reason.
- **Syntax for compiler-known constructs** beats **special-cased library items** (owner direction 2026-10-09: "syntax is preferred over special cased library constructs ... all of our langauge constructs"): first try to make an item ordinary library through a general mechanism. Where the compiler must still know its meaning, spell it as syntax or a predeclared language identifier. Ordinary library stays library, including capability services. A library intrinsic may swap an implementation without changing checking and is documented. The failure mode is a bundled type, method or service that the checker recognises by identity to grant it language semantics, for example `.catch` moved into an `ergo/effect` method the checker still special-cases, or a machine rule keyed on a bundled `Step` enum. This refines **A small regular language with deep libraries**: it decides how compiler knowledge is spelled, not whether to add it. The 2026-10-12 construct bar above narrows which syntax qualifies.
- **A primitive function plus library** beats **a construct that fails the guardrail or portability test** (owner construct bar, 2026-10-12: "we'd have to think about a good way to make them primitive rather than blocks"; the two tests are the recorded synthesis, not owner words): a construct must pass the [guardrail and portability tests](GLOSSARY.md). Otherwise the behavior is a primitive function with honest rows and library on top, as in Effect. [#134](https://github.com/cevr/ergo/issues/134) decides provide and timeout by this rule.
- **Visually distinct constructs** beat **method-shaped syntax** (owner, 2026-10-12: "they should be distinct from other already possible constructs. Like normal dot chaining and whatnot"; "I think the else block is overloading if else"): a construct must not look like ordinary dot chaining, and a well-known keyword such as `else` is not reused with a new meaning. The recorded synthesis, not owner words, sharpens this: a construct uses a keyword or block form, and a dot or pipe form is always ordinary library. Postfix constructs are therefore no longer an admissible construct spelling; existing ones stay until [#134](https://github.com/cevr/ergo/issues/134) decides, per form, between a keyword or block construct and ordinary library.
- **Composability** beats **a locally convenient construct** (owner, 2026-10-12: "the primitives have to be able to be stacked on top of each other and grow together"): a candidate that fails a [composability check](GLOSSARY.md) is redesigned or stays library, however short its source. The checks are the recorded elaboration of the owner's direction, not owner words.
- **Laws** beat **API resemblance** for provider admission (owner, 2026-10-12: "it doesn't have to have the same contract … it would be the same laws"): the RS1 suite ([#124](https://github.com/cevr/ergo/issues/124)), together with the Ergo conformance corpus, admits an effect runtime provider. Effect's own suite ([#123](https://github.com/cevr/ergo/issues/123)) is approximation evidence on the Effect surface a provider claims.
- **Go-simple signatures** beat **TypeScript-style expressiveness** (owner, 2026-10-11 and 2026-10-12: "[Go's] simplicity is the goal"; "I'm not sure if they look simple"): simplify what users write, not what the compiler checks. Elide only pass-through rows, never declared requirements, and measure each simplification against a corpus ([#135](https://github.com/cevr/ergo/issues/135)).
- **Capabilities as layers** beat **compiler-builtin providers** (owner, 2026-10-08: "layers define the impl so http is just an impl of a servicve layer"): HTTP, files, clocks and other capabilities are ordinary services whose implementations a layer provides; the compiler checks rows and ownership but does not hard-code a provider.

- Continue the authorized Wayfinder and loop work autonomously, extending finite implementation specs with evidence-backed ergonomic, guarantee and performance improvements (owner, 2026-10-06).
